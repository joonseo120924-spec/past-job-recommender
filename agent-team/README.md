# Shipyard — 앱을 만들어 스토어에 출시하는 에이전트 팀

한 줄짜리 앱 아이디어를 받아 요구사항 정리 → 화면 설계 → 구현 → 리뷰·테스트 →
스토어 심사 대비 → 빌드 → 제출까지 끌고 가는 10인 에이전트 팀.

에이전트 루프는 **Anthropic Managed Agents**가 돌린다. 이 디렉터리가 소유하는 것은
루프 바깥의 것들뿐이다: 팀 정의, 릴리스 순서, 휴먼 게이트, 크리덴셜이 필요한
호스트 사이드 툴, 실행 기록.

---

## 스택과 언어

층이 두 개다. **팀을 돌리는 것**과 **팀이 만드는 것**은 다른 언어를 쓴다.

### 컨트롤 플레인 (이 디렉터리) — Python 3.11+

| 무엇 | 선택 | 이유 |
|---|---|---|
| 언어 | Python 3.11+ | 이 레포가 이미 Python이고, Anthropic SDK가 가장 앞서 있다 |
| 에이전트 런타임 | Managed Agents (베타) | 루프·컨테이너·컨텍스트 압축을 Anthropic이 운영한다. 우리가 짤 오케스트레이션 코드가 없다 |
| 설정 | pydantic-settings | 환경변수 하나로 전부, 타입 검증 포함 |
| 팀 정의 | YAML 매니페스트 | 버전 관리되는 텍스트. `ant` CLI로도 그대로 apply 된다 |
| 기록 | SQLite | 운영할 것이 없다. 여러 릴리스를 동시에 돌리기 시작하면 Postgres로 옮기고 스키마는 그대로 쓴다 |
| HTTP | 표준 라이브러리 | GitHub REST 호출 하나 때문에 의존성을 늘리지 않는다 |

에이전트 프레임워크(LangChain, LangGraph, CrewAI 등)를 쓰지 않는다. Managed Agents가
이미 루프와 위임을 제공하므로, 그 위에 프레임워크를 한 겹 더 얹으면 추상화만 늘고
디버깅할 층이 하나 더 생긴다.

### 팀이 만드는 앱 — React Native + Expo (TypeScript)

| 무엇 | 선택 | 이유 |
|---|---|---|
| 앱 프레임워크 | React Native + Expo, TypeScript | 단일 코드베이스로 두 스토어 |
| 빌드·제출 | EAS Build / EAS Submit | **macOS 없이 iOS 빌드가 되는 유일한 짧은 경로** |
| 백엔드 | Supabase (Postgres + RLS) | 스키마를 마이그레이션 파일로 관리 = 에이전트가 다룰 수 있는 형태 |
| 테스트 | Jest + Maestro | 유닛은 컨테이너 안에서, E2E는 CI에서 |

Flutter/Dart가 아닌 이유는 성능이나 UI 품질 때문이 아니다. **리눅스 컨테이너 안에서
할 수 있는 일의 양**이 다르기 때문이다. RN + TypeScript는 코드 작성, 타입체크,
유닛 테스트, 린트까지 전부 샌드박스 안에서 끝난다. 밖으로 나가야 하는 것은
네이티브 바이너리 빌드뿐이다.

## 팀 구성

Showrunner 하나가 코디네이터이고, 나머지 아홉이 로스터다. 각자 자기 모델·자기 시스템
프롬프트·자기 툴 집합으로 **독립된 스레드**에서 돌고, 컨테이너 파일시스템만 공유한다.
서브에이전트는 코디네이터의 대화를 보지 못한다 — 그래서 넘기는 작업마다 경로와
완료 기준이 전부 들어 있어야 한다.

| 에이전트 | 모델 | 툴 | 역할 |
|---|---|---|---|
| **Showrunner** | Opus 5 (effort: xhigh) | 전체 + 커스텀 툴 | 코디네이터. 계획·통합·검증·빌드·제출 |
| Product Strategist | Opus 5 | 읽기/쓰기 + 웹 | 경쟁 조사, 범위 확정, 심사 위험 사전 표시 |
| UX Designer | Opus 5 | 읽기/쓰기 | 화면 스펙, 네 가지 상태, 디자인 토큰 |
| RN Engineer | Sonnet 5 | 전체 (웹 제외) | 화면·기능 구현. **여러 명 동시 스폰** |
| Backend Engineer | Sonnet 5 | 전체 (웹 제외) | 스키마, 마이그레이션, RLS |
| Test Engineer | Sonnet 5 | 전체 (웹 제외) | 유닛 + E2E |
| Code Reviewer | Opus 5 | **읽기 전용** | 리뷰. 같은 변경에 2~3명 병렬 |
| Store Compliance | Opus 5 | 읽기/쓰기 + 웹 | 심사 가이드라인 대조, 리젝 사전 차단 |
| Release Engineer | Sonnet 5 | 전체 (검색 제외) | app.json, eas.json, 버전, CI |
| Store Copywriter | Sonnet 5 | 읽기/쓰기 + 검색 | 리스팅 카피, ASO, 로컬라이제이션 |

모델 배치의 원칙: **판단이 필요한 자리에 Opus, 읽기와 타이핑이 많은 자리에 Sonnet.**
세션 중간에 모델을 바꾸면 프롬프트 캐시가 통째로 깨지므로, 싼 모델로 "갈아타지" 않고
싼 모델로 도는 서브에이전트를 따로 스폰한다. 로스터 멤버는 각자 자기 요율로 과금된다.

Code Reviewer가 읽기 전용인 것은 실수가 아니라 설계다. 고칠 수 있는 리뷰어는
리뷰 대신 수정을 하고, 그러면 아무도 그 수정을 리뷰하지 않는다.

## 릴리스 파이프라인

한 릴리스 = 한 세션이다. 단계마다 세션을 새로 만들지 않는다 — 컨테이너 파일시스템에
코드가 있고, 리뷰어 스레드가 앞서 본 것을 기억하고 있어야 하기 때문이다.

```
discovery → spec →[게이트]→ implement → harden → compliance
                                                      ↓
                              submit ←[게이트]← binary ← release_prep
```

| 단계 | 하는 일 | 게이트 |
|---|---|---|
| `discovery` | 경쟁 조사, 범위 확정, 기술 스택 결정 | |
| `spec` | 화면 스펙, 데이터 모델, 둘의 대조 | |
| `implement` | 스캐폴드 + 화면 병렬 구현 | **컨셉 승인** |
| `harden` | 병렬 리뷰 → 수정 → 테스트 | |
| `compliance` | 심사 가이드라인 대조, BLOCKER 처리 | |
| `release_prep` | 빌드 설정 + 스토어 리스팅 | |
| `binary` | 외부 CI에서 바이너리 빌드 | |
| `submit` | 제출 전 5항목 점검 → 업로드 | **빌드 승인 + 제출 승인** |

게이트는 네 종류이고 그중 하나는 설정으로 끌 수 없다.

| 게이트 | 언제 | 자동 승인 |
|---|---|---|
| CONCEPT | 구현 시작 전 | 가능 |
| BUILD | CI 트리거 전 | 가능 |
| DECISION | 에이전트가 판단을 못 할 때 | 가능 |
| **STORE_SUBMISSION** | 스토어 업로드 직전 | **불가능** |

`auto_approve_gates`는 개발 편의를 위한 장치이지, 실제 사용자에게 앱을 내보내는
결정까지 위임하라는 뜻이 아니다. 이 예외를 설정으로 만들 수 있게 하지 않은 것은 의도적이다.
비대화형 환경(승인할 사람이 없는 곳)에서는 모든 게이트가 **거절**로 처리된다.

## 백엔드 연결

`SHIPYARD_SUPABASE_URL` / `SHIPYARD_SUPABASE_PUBLISHABLE_KEY` 를 설정하면, 릴리스를 시작할 때
`shipyard/backend.py` 가 두 가지를 세션에 넘긴다.

**1. 실행 시점에 조회한 프로젝트 설정** — 어떤 로그인 방식이 켜져 있는지, 이메일 확인이
필요한지, 익명 로그인이 되는지. 문서에 박아두지 않고 매번 `/auth/v1/settings` 를 조회하는
이유는, 콘솔에서 설정을 바꾼 순간 박아둔 값이 거짓말이 되기 때문이다. 팀은 그 거짓말에 맞춰
로그인 화면을 만든다. 조회에 실패해도 릴리스를 막지는 않고, 사실이 하나 줄었다고 알린다.

**2. 연결 계약** — 에이전트에게 "Supabase를 쓰라"고만 말하면 실행마다 다르게 배선한다.
그래서 못박는다.

| 항목 | 값 |
|---|---|
| 클라이언트 위치 | `lib/supabase.ts` 한 곳 |
| 환경변수 | `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` |
| 세션 저장 | `@react-native-async-storage/async-storage`, `detectSessionInUrl: false` |

publishable 키는 앱 번들에 실려 나가도록 설계된 키다. 즉 **이 키를 가진 사람은 누구나
REST API를 직접 호출할 수 있고, 그 권한 경계는 RLS 하나뿐이다.** 그래서 테이블 생성
마이그레이션과 RLS 정책이 같은 마이그레이션에 들어가야 한다는 요구가 시스템 프롬프트와
연결 계약 양쪽에 들어 있다. `service_role` 키는 이 팀이 다루지 않으며, 설정에 있으면
`doctor` 가 거부한다.

## 샌드박스 밖에 있는 것들, 그리고 왜

**iOS 빌드는 여기서 불가능하다.** 코드 서명과 Xcode는 macOS를 요구하고 세션 컨테이너는
리눅스다. 이건 우회할 수 있는 제약이 아니다. 그래서 빌드는 `trigger_build` 커스텀 툴로
밖으로 나가고, 두 가지 백엔드를 지원한다.

- **GitHub Actions** — macOS 러너. 서명 키가 GitHub Secrets에 있으면 컨트롤 플레인
  호스트에도 키가 없어도 된다. 워크플로에 `run-name: ${{ inputs.correlation_id }}` 한 줄이 필요하다.
- **EAS Build** — 로컬 `eas` CLI. macOS 없이 iOS 빌드가 되는 가장 짧은 경로.

물리적 제약에서 시작했지만 보안 이점이 따라온다. 커스텀 툴은 컨트롤 플레인에서 실행되므로
**서명 키와 스토어 크리덴셜이 샌드박스에 들어간 적이 없다.** 에이전트가 쓴 코드가
그 컨테이너 안에서 실행되는 걸 생각하면 이건 작은 차이가 아니다.

크리덴셜이 사는 곳:

| 비밀 | 어디에 | 샌드박스가 볼 수 있나 |
|---|---|---|
| Supabase publishable 키 | 앱 설정 (클라이언트용으로 설계된 키) | 예 — 그래야 앱이 돈다 |
| Supabase service_role 키 | **어디에도 두지 않는다** | 아니오 |
| GitHub 토큰 (저장소 마운트) | 세션 리소스, git 프록시가 주입 | 아니오 |
| GitHub 토큰 (CI 트리거) | 컨트롤 플레인 프로세스 | 아니오 |
| 서명 키 / 스토어 계정 | CI 시크릿 또는 EAS | 아니오 |

publishable 키의 권한 경계는 **RLS 하나뿐이다.** RLS를 켜지 않은 테이블은 그 키를 가진
누구에게나 열려 있다. Backend Engineer가 테이블과 정책을 같이 만들도록 시스템 프롬프트에
박아둔 이유다.

## 실행

```bash
pip install -r agent-team/requirements.txt
cd agent-team
cp .env.example .env        # 값을 채운다

python -m shipyard env apply    # 컨테이너 환경 생성 → ENVIRONMENT_ID 를 .env 에
python -m shipyard apply        # 에이전트 10개를 API에 반영 (멱등)
python -m shipyard doctor       # 설정이 실제로 맞는지 점검

python -m shipyard run "달리기 기록을 지도 위에 남기는 앱" --platforms "ios, android"
```

중간에 멈췄다면:

```bash
python -m shipyard status
python -m shipyard resume --start compliance
```

단계 하나만 돌려보려면 `--start spec --stop-after spec`.

`apply`는 멱등하다. 매니페스트가 안 바뀌었으면 API를 부르지 않고, 바뀌었으면 해당
에이전트만 업데이트한다(버전이 올라간다). 이미 돌고 있는 세션은 자기가 고정한 버전을
계속 쓴다.

테스트:

```bash
cd agent-team && pytest
```

64개 테스트가 전부 API 없이 돈다. 매니페스트 검증(`tests/test_manifests.py`)이 따로 있는
이유는 레포의 `tests/test_data_integrity.py`와 같다 — 팀 정의가 조용히 망가지는 것이
가장 흔한 실패 원인이고, 그건 코드 테스트로 잡히지 않는다.

## 비용

세션당 하드 상한(`SHIPYARD_SESSION_BUDGET_USD`)을 걸어두는 것을 강력히 권한다. 상한에
도달하면 세션이 `budget_reached`로 멈추고, 상한을 올리거나 없애야 이어진다.

| 모델 | 입력 / 출력 ($/1M) |
|---|---|
| Opus 5 | 5 / 25 |
| Sonnet 5 | 2 / 10 |
| Haiku 4.5 | 1 / 5 |

실제 비용은 세션의 `usage.list_cost`에 있다. `shipyard/models.py`의 추정 함수는 캐시
할인을 반영하지 않으므로 항상 상한선으로 보면 된다.

## 알려진 한계

정직하게 적어둔다. 이 한계들은 프롬프트를 다듬어서 해결되지 않는다.

1. **이 팀은 앱을 출시할 수 없다. 출시 준비까지만 한다.** 개발자 계정, 세금·은행 정보,
   앱 심사 응답, 계정 소유권은 전부 사람의 것이다. `submit_to_store`가 하는 일은
   바이너리 업로드까지이고, 그마저도 사람의 승인을 거친다.

2. **심사 통과를 보장하지 않는다.** Store Compliance는 가이드라인을 읽고 코드와 대조할 뿐,
   실제 심사관이 무엇을 문제 삼을지는 모른다. 리젝 확률을 낮추는 장치이지 없애는 장치가 아니다.

3. **바이너리를 실행해본 적이 없다.** 컨테이너 안에서 타입체크와 유닛 테스트는 돌지만,
   실제 기기에서 앱이 열리는지는 아무도 확인하지 않았다. 첫 제출을 `internal` 트랙으로
   권하는 이유이고, 이건 도구로 해결되지 않는다 — 사람이 한 번 열어봐야 한다.

4. **파일 범위 충돌은 프롬프트로만 막고 있다.** 스레드들이 같은 컨테이너 파일시스템을
   공유하는데, 겹치지 않게 나누는 책임이 Showrunner의 판단에 있다. 락도, 검증도 없다.
   병렬 엔지니어를 늘릴수록 이 지점이 먼저 깨진다.

5. **서브에이전트 보고를 검증하는 것도 Showrunner의 판단이다.** 시스템 프롬프트에
   "믿지 말고 직접 확인하라"고 적어뒀지만, 그게 지켜지는지 강제하는 코드는 없다.

6. **심사 상태를 추적하지 않는다.** 업로드 이후는 이 팀의 범위 밖이다. 심사 결과,
   리젝 사유, 재제출은 사람이 스토어 콘솔에서 처리한다.

7. **GitHub Actions 백엔드로 빌드하면 `submit_to_store`가 동작하지 않는다.** EAS가 그
   빌드를 모르기 때문이다. 그 조합에서는 제출도 같은 워크플로 안에서 fastlane으로
   처리해야 하며, 지금은 그 경로가 구현돼 있지 않고 에러로 명확히 알린다.

8. **`agents.update` 바인딩은 실제 API로 검증하지 못했다.** 이 디렉터리의 코드는 SDK 문서를
   근거로 작성했지만, 세션을 실제로 띄워본 것은 아니다. 처음 `apply`를 돌릴 때 여기서
   에러가 나면 그건 바인딩 이름 문제일 가능성이 높다.
