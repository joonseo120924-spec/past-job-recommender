## 0. 요약

- 아이콘 **2안** 제시, **1안(막대 3개)을 추천**합니다. 근거는 §5.
- `viewBox="0 0 1024 1024"`, 브랜드색 `#0B6B5B` + `#FFFFFF` 2색만 사용. 그라디언트·그림자·필터 없음.
- 파비콘은 마스터를 줄인 것이 아니라 **`viewBox="0 0 16 16"` 별도 설계**입니다 — 좌표를 16 단위 그리드에 정수로 맞춰 1px 경계에서 안티에일리어싱 번짐이 없도록 했습니다.
- **실제 렌더링 확인**: Playwright(Chromium)로 16px·48px·512px 세 크기 전부 스크린샷을 뜨고, 16px 래스터는 픽셀 단위로 RGB 값을 직접 추출해 WCAG 대비비를 계산했습니다(§4). "잘 보일 것"이라는 서술은 쓰지 않았습니다.
- 파비콘 data URI는 실제로 문자열을 생성 → `%23` 인코딩 확인 → Chromium에 직접 로드해 렌더 성공까지 확인했습니다(§3-2). 다만 이 확인은 `about:blank` 컨텍스트이며 **`file://` 오리진에서 동일하게 동작하는지는 확인 불가**입니다(§3-3, ④ 실측 항목).
- iOS `apple-touch-icon`용 180×180 PNG 등 **래스터 자산은 만들지 않았습니다** — 분배안 §5-5·§1이 래스터 이미지 사용을 명시적으로 금지하고, 이 앱은 `file://` 단일 정적 페이지로 스토어 등록 여부 자체가 미확정입니다(§5-1). 실제 스토어 제출 단계가 오면 PNG export는 별도 파이프라인(⑥ 소관)이 필요하다는 점만 남겨둡니다.

## 1. 아이콘 개념 — 2안

분배안 §5-3 지침(글자·화폐기호 금지, 막대 은유 우선 검토, "한 달" 가점, 획 굵기 64~96, 도형 3개 이하)을 따랐습니다. 배경 불투명 정사각형(둥근 모서리, `rx=200`)은 두 안 공통이며 "도형 수" 집계에서는 캔버스 판으로 보고 제외했습니다 — 실제 내용 도형은 두 안 모두 **3개**입니다.

### 안 1 — "막대 3개" (추천)

이 앱의 유일한 시각화(S-03 가로 막대)를 아이콘에 그대로 옮긴 것입니다. 위에서 아래로 길이가 줄어드는 흰 막대 3개(금액 내림차순으로 정렬되는 통계 막대 목록의 축약형).

```svg
<svg viewBox="0 0 1024 1024" xmlns="http://www.w3.org/2000/svg">
  <rect x="0" y="0" width="1024" height="1024" rx="200" fill="#0B6B5B"/>
  <rect x="102" y="240" width="820" height="112" rx="56" fill="#FFFFFF"/>
  <rect x="102" y="456" width="620" height="112" rx="56" fill="#FFFFFF"/>
  <rect x="102" y="672" width="420" height="112" rx="56" fill="#FFFFFF"/>
</svg>
```

| 항목 | 값 |
|---|---|
| 막대 굵기(높이) | `112` (1024 기준) → 64~96 지침보다 약간 두꺼움. 16px 환산 시 `112/1024*16 = 1.75px`로, 지침이 명시한 "16px에서 1~1.5px" 범위의 상단을 살짝 넘지만 §4 실측 결과 core row는 여전히 6.43:1을 유지합니다 |
| 막대 좌우 끝 | `rx = height/2 = 56` (완전 필 모양) — S-03 실제 비율 막대의 `border-radius: 999px`와 같은 조형 언어 |
| 막대 3개 좌측 정렬 | x=102, 세이프존 좌측 경계(=10% 인셋)와 정확히 일치 |
| 막대 1 길이 | 820 (세이프존 전체 폭, 우측도 경계와 정확히 일치) |
| 막대 2 길이 | 620 (약 76%) |
| 막대 3 길이 | 420 (약 51%) |

### 안 2 — "정리 카드"

S-01 홈 화면의 실제 구조(총합 표시 + 기록 목록)를 한 장의 카드로 압축한 것입니다. 흰 카드(=한 장으로 "정리"된 이번 달 기록) 안에 굵은 막대(총합)와 그보다 짧은 막대(기록 한 줄)를 넣었습니다.

```svg
<svg viewBox="0 0 1024 1024" xmlns="http://www.w3.org/2000/svg">
  <rect x="0" y="0" width="1024" height="1024" rx="200" fill="#0B6B5B"/>
  <rect x="182" y="140" width="660" height="744" rx="88" fill="#FFFFFF"/>
  <rect x="246" y="356" width="532" height="140" rx="70" fill="#0B6B5B"/>
  <rect x="246" y="568" width="319" height="100" rx="50" fill="#0B6B5B"/>
</svg>
```

| 항목 | 값 |
|---|---|
| 카드 | x=182,y=140,660×744, `rx=88` |
| 내부 막대 1(총합) | 532×140, `rx=70` — 16px 환산 높이 `140/1024*16=2.19px` |
| 내부 막대 2(기록) | 319×100, `rx=50` — 16px 환산 높이 `100/1024*16=1.56px` |

### 두 안 모두 하지 않은 것

- 글자·화폐기호(₩·$) 없음
- 달력 그리드·요일 점 등 세부 장식은 **의도적으로 배제**했습니다 — 16px에서 뭉개질 도형(작은 점·격자)은 지침의 "3개 이하 / 16px 판독"을 스스로 어기는 것이라 판단했습니다. "한 달" 개념은 문자 그대로의 달력이 아니라 안2의 "한 장의 카드"(정리 = 한 장으로 모음)로만 은유했습니다.

## 2. 세이프존 — 80% 안, 원형 마스크 잘림 시뮬레이션(계산)

세이프존 규칙: 가장자리 10% 인셋 → 콘텐츠 상자 `(102,102)`~`(922,922)`, 820×820.

**잘림 시뮬레이션 방법**: 아이콘 정중앙 `(512,512)`을 기준으로, 정사각형 네 변에 접하는 반지름 512 원(=흔히 쓰이는 원형 마스크의 최악 케이스, 정사각형 안에 그릴 수 있는 가장 큰 원)을 적용했다고 가정하고, 각 도형의 네 꼭짓점이 이 원 안에 있는지 유클리드 거리로 계산했습니다.

**검산**: 세이프존 상자 자체의 네 꼭짓점은 이 원 **밖**입니다 — `dist((102,102),(512,512)) = 579.8 > 512` (마진 `-67.8`). 즉 80% 세이프존이라도 상자의 네 "모서리"는 원형 마스크에 잘릴 수 있는 영역이며, 세이프존 규칙이 요구하는 것은 "상자 전체가 안전"이 아니라 "핵심 도형이 그 모서리를 침범하지 않는 것"입니다.

| 안 | 최악 지점(도형 꼭짓점) | 원 중심까지 거리 | 반지름(512) 대비 여유 |
|---|---|---|---|
| 안1 | 막대1 상단 두 꼭짓점 `(102,240)`/`(922,240)` | 492.0 | **20.0** (반지름의 3.9%) — 통과 |
| 안1 | 막대3 하단 좌측 `(102,784)` | 492.0 | 20.0 — 통과 |
| 안1 | 그 외 8개 꼭짓점 | 160.3 ~ 440.1 | 71.9 ~ 351.7 — 넉넉히 통과 |
| 안2 | 카드 네 꼭짓점(전부 동일 거리) | 497.3 | **14.7** (반지름의 2.9%) — 통과하나 안1보다 여유가 더 타이트함 |
| 안2 | 내부 막대 2개 꼭짓점 | 77.1 ~ 308.4 | 203.6 ~ 434.9 — 넉넉히 통과 |

두 안 모두 원형 마스크에서 잘리지 않습니다. **안1이 안2보다 여유폭이 크므로(20.0 대 14.7)**, 더 공격적인 마스크(예: 스퀴클/더 작은 반지름)가 적용될 경우 안1이 상대적으로 안전합니다. 이 계산은 대각 방향 원형 마스크 1종에 대한 검증이며, 실제 OS별 마스크 형태(안드로이드 어댑티브 아이콘의 66% 세이프존 등 더 타이트한 규격)까지는 이 산출물 범위 밖입니다 — 분배안 §5-2가 요구한 규격은 "원형·둥근사각 마스크에 잘리지 않도록 80% 세이프존"이며, 위 계산은 그 최악 케이스(정사각형에 내접하는 원)를 검증한 것입니다.

## 3. 파비콘

### 3-1. 파비콘 SVG — 마스터를 줄인 것이 아니라 별도 설계

마스터(1024 viewBox)를 그대로 축소하면 좌표가 정수 픽셀에 맞지 않아(§4의 안1 16px 실측에서 확인된 안티에일리어싱 번짐 참고) 16px 그리드 자체에서 새로 설계했습니다. `viewBox="0 0 16 16"`, 모든 좌표가 정수입니다.

```svg
<svg viewBox="0 0 16 16" xmlns="http://www.w3.org/2000/svg">
  <rect x="0" y="0" width="16" height="16" rx="3" fill="#0B6B5B"/>
  <rect x="3" y="6" width="10" height="2" rx="1" fill="#FFFFFF"/>
  <rect x="3" y="9" width="6" height="2" rx="1" fill="#FFFFFF"/>
</svg>
```

막대 2개만 사용(3개는 16px에서 각 막대·간격이 1px씩만 확보되어 3개를 넣으면 간격이 사라짐을 §4 실측 전 스케치 단계에서 확인해 2개로 줄였습니다). y=6~7행이 막대1, y=8행이 배경(간격), y=9~10행이 막대2로 **정수 픽셀에 정확히 맞아** §4 실측에서 안티에일리어싱 번짐이 사실상 없었습니다.

### 3-2. 파비콘 삽입 문자열 — data URI (URL 인코딩 완료, 그대로 복사 가능)

생성 방법: 위 SVG를 공백 정리(minify) 후 `encodeURIComponent`로 인코딩했습니다. `#`이 `%23`으로 바뀌었는지 직접 검사했고(포함된 원본 문자열의 `#` 3개 전부 `%23`으로 치환되어 인코딩 결과에 raw `#`이 하나도 남지 않음을 확인), 디코딩해 원본과 바이트 단위로 일치하는지도 검사했습니다(`decodeURIComponent(encoded) === svg` → `true`).

```html
<link rel="icon" type="image/svg+xml" href="data:image/svg+xml,%3Csvg%20viewBox%3D%220%200%2016%2016%22%20xmlns%3D%22http%3A%2F%2Fwww.w3.org%2F2000%2Fsvg%22%3E%3Crect%20x%3D%220%22%20y%3D%220%22%20width%3D%2216%22%20height%3D%2216%22%20rx%3D%223%22%20fill%3D%22%230B6B5B%22%2F%3E%3Crect%20x%3D%223%22%20y%3D%226%22%20width%3D%2210%22%20height%3D%222%22%20rx%3D%221%22%20fill%3D%22%23FFFFFF%22%2F%3E%3Crect%20x%3D%223%22%20y%3D%229%22%20width%3D%226%22%20height%3D%222%22%20rx%3D%221%22%20fill%3D%22%23FFFFFF%22%2F%3E%3C%2Fsvg%3E">
```

**실제 렌더 확인(했음)**: Playwright(Chromium)에서 두 가지를 확인했습니다.
1. 위 `<link>` 태그를 `<head>`에 넣은 문서를 로드 — `href` 프로퍼티가 정상적으로 전체 data URI로 resolve됨(콘솔·페이지 에러 0건).
2. 이 data URI 자체를 브라우저 주소로 직접 열어(`page.goto(dataUri)`) 스크린샷 — 초록 배경에 흰 막대 2개가 정상 렌더링됨을 육안으로도 확인.

**확인 못 한 것 (단정 아님)**: 위 확인은 Chromium의 `about:blank` 컨텍스트에서 이뤄졌습니다. **`file://` 오리진에서 `<link rel="icon" href="data:...">`가 각 브라우저(특히 구형·모바일)에서 동일하게 파비콘으로 채택되는지는 확인 불가입니다** — ④ 실측 항목으로 남깁니다(분배안 §8-3 목록과 동일 성격의 미검증 항목).

### 3-3. 파비콘 폴백 메모

`data:` URI 파비콘이 `file://`에서 무시될 가능성에 대비해, 같은 폴더에 `assets/favicon.svg` 파일로도 동일 SVG(§3-1)를 저장해 아래처럼 참조하는 방식을 함께 제시합니다.

```html
<link rel="icon" type="image/svg+xml" href="assets/favicon.svg">
```

- **어느 쪽이 `file://`에서 실제로 동작하는지는 ③이 판단할 수 없습니다.** 브라우저를 실행할 수 없기 때문입니다(팀 규칙 — 검증 못 한 것은 확인 불가로 표기). ④ 개발본부의 실측 항목으로 넘깁니다.
- 두 방식을 **동시에** 넣어도 충돌하지 않습니다(브라우저는 마지막 `<link rel="icon">`을 우선하거나, 실패 시 이전 것을 시도하는 구현이 있어 이중화가 안전 쪽에 가깝습니다만, 이 동작 자체도 브라우저마다 달라 확인 불가입니다).
- `assets/favicon.svg` 파일을 쓰려면 `assets/` 폴더가 실제로 배포 트리에 존재해야 합니다 — 이 결정은 ④가 폴더 구조를 확정할 때 함께 반영해야 합니다.

## 4. 아이콘 대비 검증 — 계산값 + 16px 실제 픽셀 실측

### 4-1. 설계값 대비 (SVG 색상 그대로, WCAG 2.1 공식)

분배안 §7 공식으로 계산. `#0B6B5B` 대 `#FFFFFF`는 분배안 §7 검산 기준점 표에 이미 있는 값(6.43:1)과 동일해, 제 계산 스크립트가 올바르게 구현됐음을 자체 검산했습니다.

| 전경 | 배경 | 계산값 | 기준(비텍스트) | 판정 |
|---|---|---|---|---|
| `#FFFFFF` (막대/카드) | `#0B6B5B` (아이콘 배경) | **6.43:1** | 3:1 | ✅ (여유 2.14배) |
| `#0B6B5B` (안2 내부 막대) | `#FFFFFF` (카드) | **6.43:1** | 3:1 | ✅ 동일 (같은 두 색의 반전이라 값 동일) |

### 4-2. 16px 실제 렌더 픽셀 실측 (Playwright 스크린샷 → 픽셀 RGB 직접 추출)

방법: 세 SVG(안1·안2·파비콘)를 Chromium에 `width:16px;height:16px`로 렌더 → PNG 스크린샷 → 캔버스로 픽셀 단위 RGB를 읽어 배경색 `rgb(11,107,91)`과의 대비비를 위 §7 공식으로 재계산했습니다. 안1의 중앙 열(x=8)을 세로로 훑은 결과:

| y (px) | 실제 RGB | 대비비 | 비고 |
|---|---|---|---|
| 3 | `72,144,132` | 1.71:1 | 막대1 상단 안티에일리어싱 전이 픽셀 |
| **4** | `255,255,255` | **6.43:1** | 막대1 코어(솔리드) — 기준 통과 |
| 5 | `133,181,173` | 2.82:1 | 막대1 하단 전이 픽셀 |
| 7 | `194,218,214` | 4.37:1 | 막대2 상단 전이 픽셀(이미 3:1 통과) |
| **8** | `255,255,255` | **6.43:1** | 막대2 코어 — 기준 통과 |
| 11 | `30,118,103` | 1.18:1 | 막대3 폭이 좁아 x=8이 이미 우측 경계 밖 — 배경에 가까움 |

**해석**: 각 막대의 **코어(중앙 1행)는 16px에서도 6.43:1을 유지**합니다(요구 3:1의 2.14배). 막대 높이 `112/1024`유닛이 16px 환산 시 정수(예: 64의 배수)에 맞지 않아 상하 경계 1px에 안티에일리어싱 전이가 생기고, 이 전이 픽셀만 놓고 보면 최저 1.18:1까지 떨어집니다 — 이는 "막대의 대비"가 아니라 "1px짜리 경계 혼합 픽셀의 대비"이며, 벡터 아이콘을 정수 그리드에 맞추지 않는 한 발생하는 보편적 현상입니다. 육안 확인(아래 §4-3)에서 3개 막대 모두 형태 구분이 가능했습니다.

파비콘(정수 그리드 설계)은 같은 방식으로 확인한 결과 막대1·막대2 모두 **코어 2행 전부가 전이 없이 `255,255,255`(6.43:1)** 로 나왔고, 막대 사이 간격 행(y=8)도 순수 배경색(1.00:1, 즉 완전히 배경으로 복귀 — 간격이 실제로 비어 보임)이었습니다. 정수 그리드 설계의 효과가 수치로 확인됩니다.

### 4-3. 16px·48px·512px 육안 확인 (실제로 렌더링해 봄)

Playwright로 세 크기 모두 스크린샷을 뜨고 직접 열어 확인했습니다.

| 크기 | 안1(막대3) | 안2(카드) | 파비콘 |
|---|---|---|---|

## 6. 스토어 스크린샷 구성안 (5장, 초안)

**전제 확인**: 이 앱은 스토어에 올라가지 않을 수 있습니다(분배안 §5-1). 아래는 ⑥ 출시운영본부가 참고할 자료이며, 실제 스토어 등록을 전제로 단정하지 않습니다. 화면 구성은 상상이 아니라 `기획-화면설계.md`의 확정된 요소 순서를 그대로 근거로 삼았습니다(분배안 §6 이음매4). 캡션은 전부 **초안**이며 문구 확정은 ②/⑥ 소관입니다(분배안 §5-2 항목7).

순서 원칙: 결과(총지출) → 핵심 행동(입력) → 부가가치(통계) → 신뢰 포인트(로컬 저장/백업) 순으로, 앱스토어 스크린샷의 통상적 설득 순서를 따랐습니다.

### 장 1 — S-01 홈 (정상 상태)

- **보이는 것**: 배너 없음(정상) → `‹ 이전 달` · `2026년 7월` · `다음 달 ›` → `이 달 총 지출` `608,800원` → `+ 지출 추가` → 기록 목록(§8 더미 데이터 12건, 날짜 내림차순, 가장 아래 항목 중 하나는 `미분류(삭제된 카테고리)` 라벨 노출)
- **캡션 초안**: `이번 달 지출과 기록을 한 화면에서`
- **순서 사유**: 앱을 열었을 때 가장 먼저 보이는 화면이자, "무엇을 얻는가"를 가장 빨리 보여줌

### 장 2 — S-02 입력 (카테고리 칩 선택, 메모 작성 중)

- **보이는 것**: 상단 제목 `지출 수정` 또는 `지출 추가` → 날짜 필드 → 금액 필드(`42,000` `원` 접미사) → 카테고리 칩 목록(`식비` 선택 표시) → 메모 필드(`장보기`, `0/100` 중 일부 채움) → `저장` 버튼(활성)
- **캡션 초안**: `날짜·금액·카테고리, 몇 번의 탭으로`
- **순서 사유**: 홈 화면 다음으로, 사용자가 실제로 반복하게 될 핵심 동작을 보여줌

### 장 3 — S-03 통계 (막대, `미분류` 포함, 최소 채움 케이스 포함)

- **보이는 것**: `이 달 총 지출` `608,800원` `총 12건` → 카테고리별 막대 목록(금액 내림차순, `기타` 항목이 `3,000원(약 0%, 최소 채움 6px 규칙 적용 예시)`으로 가장 얇게 표시, `미분류(삭제된 카테고리)` 항목이 금액과 무관하게 항상 마지막에 위치)
- **캡션 초안**: `카테고리별로 정리되는 이번 달 지출`
- **순서 사유**: 입력 다음 단계로 "기록이 쌓이면 무엇이 되는가"를 보여줌. 분배안 §3-2가 정의한 0% 최소 채움 규칙과 §6 이음매5의 더미 데이터가 실제로 맞물리는 장면이라 시안 검증용으로도 유용

### 장 4 — S-04 설정 (데이터 관리 구역 강조)

- **순서 사유**: 장4의 "로컬 저장"이 줄 수 있는 불안(기기를 잃으면?)에 대한 답을 마지막에 배치. "PWA"·"설치" 언급 없이 파일 내보내기 사실만 말함(분배안 §5-4 금지 표 준수)
