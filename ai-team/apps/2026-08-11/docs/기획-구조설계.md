### 1-2. P-7 의 구체적 금지 사항 (이것이 실제 사고를 만듭니다)

`new Date().toISOString().slice(0,10)` 은 **UTC 기준**입니다. KST(UTC+9) 에서 08:00 이전에 실행하면 전날 날짜가 나옵니다. 오늘 날짜를 만드는 유일한 허용 방법은 아래 하나입니다.

```js
// JR.model.today() 의 내부 구현 — 이 방식 외의 오늘 날짜 계산을 금지합니다
function today() {
  var d = new Date();
  return pad4(d.getFullYear()) + '-' + pad2(d.getMonth() + 1) + '-' + pad2(d.getDate());
}
function pad2(n) { return n < 10 ? '0' + n : '' + n; }
function pad4(n) { return n < 10 ? '000' + n : n < 100 ? '00' + n : n < 1000 ? '0' + n : '' + n; }
```

`createdAt` 만 예외적으로 `Date.now()` 정수(epoch ms)를 씁니다. 이것은 표시용이 아니라 **정렬 tie-break 전용**이므로 타임존 영향을 받지 않습니다.

2. `memo` — lone surrogate 제거(E-122). 제거가 발생하면 T 슬롯 알림
3. `memo` — 제어문자(U+0000~U+001F, U+007F) 제거. 단 제거 사실은 알리지 않음(§7-9 폴백표)
4. `amount` — `Math.trunc` 하지 않습니다. 소수가 들어오면 **거부**(E-105). 조용히 자르면 사용자가 모르는 사이 금액이 바뀝니다
5. `date` — 그대로. 형식이 어긋나면 거부(E-107)

### 2-5. ID 생성 규칙

`crypto.randomUUID()` 를 **쓰지 않습니다.** secure context 를 요구하는 API 인데 `file://` 이 secure context 로 취급되는지 확정할 수 없습니다(§9 확인필요-4). 아래 방식은 외부 의존이 0이고 ES5 로 동작합니다.

```js
var _seq = 0;
function newId(prefix) {              // prefix: 'e' | 'c'
  _seq = (_seq + 1) % 1679616;        // 36^4
  return prefix + '_' +
         Date.now().toString(36) + '_' +
         _seq.toString(36) + '_' +
         Math.floor(Math.random() * 1679616).toString(36);
}
```

**충돌 방어**: 삽입 직전 기존 배열에 같은 `id` 가 있는지 확인합니다. 있으면 `newId` 를 다시 호출하며 최대 5회 재시도합니다. 5회 모두 충돌하면 저장을 중단하고 `{ok:false, code:'E-507'}` 를 반환합니다(현실적으로 도달 불가능하지만 무한 루프를 만들지 않기 위해 상한을 둡니다).

**한 세션 안에서 `_seq` 가 단조 증가**하므로 같은 밀리초에 생성된 두 기록도 `id` 가 다릅니다. 이것이 §4-1 정렬의 최종 tie-break 를 결정적으로 만듭니다.

### 2-6. 카테고리 이름 중복 비교 규칙

`localeCompare` 와 `toLocaleLowerCase` 를 **쓰지 않습니다.** 브라우저·OS 로케일에 따라 결과가 달라져 "이 기기에서는 중복인데 저 기기에서는 아닌" 상태가 생깁니다.

```js
function normName(s) {
  return String(s).trim().replace(/\s+/g, ' ').toLowerCase();
}
// 중복 판정: normName(a) === normName(b)
```

- 앞뒤 공백 제거, 연속 공백 1칸으로 축약, ASCII 소문자화(`toLowerCase` 는 로케일 비의존)
- 한글은 대소문자가 없으므로 영향 없음. `식비` 와 `식비 ` 는 중복, `식비` 와 `식 비` 는 서로 다름
- 유니코드 정규화(`normalize('NFC')`)는 **하지 않습니다.** 한글 자모 조합형 입력이 들어오는 경로가 이 앱에 없고(모든 입력은 IME 확정 후 들어옴), `String.prototype.normalize` 의 `file://` 가용성을 별도로 검증해야 하는 비용이 이득보다 큽니다

### 2-7. 카테고리 삭제 시 기존 기록 처리 (데이터 규칙 — §5 경계상 SA 영역)

**확정: 기록을 삭제하지 않고, `categoryId` 를 그대로 남깁니다.**

| 선택지 | 채택 여부 | 사유 |
|---|---|---|
| (a) 그 카테고리를 쓰는 기록도 함께 삭제 | 채택 안 함 | 사용자가 잃는 것이 카테고리 1개가 아니라 금액 기록 N건이 됩니다. 되돌릴 수단이 없습니다 |
| (b) `기타`로 자동 재지정 | 채택 안 함 | `기타` 자체도 삭제 가능하므로 재지정 대상이 없을 수 있습니다. 또 어느 기록이 원래 무엇이었는지 정보가 소실됩니다 |
| **(c) `categoryId` 유지 (dangling 허용)** | **채택** | 원 데이터가 보존됩니다. 사용자가 결과를 보고 판단할 수 있습니다 |

**dangling 처리 규칙**

1. 목록·통계에서 존재하지 않는 `categoryId` 를 만나면 표시명 기본값은 문자열 `삭제된 카테고리` 입니다. (이 라벨의 최종 문구권은 `ux-designer` 에 있을 수 있어 Q-007 로 남겼습니다. 데이터 계약은 라벨이 아니라 아래 2번의 `categoryId` 값입니다.)
2. 통계(`JR.stats.byCategory`)에서 dangling 기록은 **서로 다른 id 여도 하나의 항목으로 합산**하며, 그 항목의 `categoryId` 는 예약어 `__deleted__` 입니다. `__deleted__` 는 저장되는 값이 아니라 집계 결과에만 등장하는 값입니다.
3. `isDeletedCategory: true` 플래그를 집계 결과 항목에 붙여 UI 가 구분할 수 있게 합니다.
4. **같은 이름으로 카테고리를 다시 만들어도 자동 복구되지 않습니다.** 새 카테고리는 새 `id` 를 받기 때문입니다. 이것은 의도된 동작이며 v1 에 재지정 기능을 넣지 않습니다(F-07 범위 밖).
5. 삭제 API 는 영향받는 건수를 반환합니다 — `{ok:true, data:{orphanedExpenseCount: 30}}`. `ux-designer` 가 확인 대화상자에 이 숫자를 쓸 수 있습니다.

## 3. localStorage 키 설계

### 3-1. 키 목록 (전부 확정 — 이 외의 키를 만들지 않습니다)

| 키 | 내용 | 필수 | 백업본 |

| `jr.v1.expenses` | `Expense[]` | O | `jr.v1.expenses.bak` |
| `jr.v1.categories` | `Category[]` | O | `jr.v1.categories.bak` |

| `jr.v1.rollback` | 가져오기 트랜잭션 중에만 존재하는 직전 전체 스냅샷 | X | — |

| `jr.v1.corrupt.<epochMs>` | 파싱 불가였던 원본 문자열 보관. **최대 3개** 유지, 초과 시 가장 오래된 것부터 삭제 | X | — |

**분할한 이유**를 명시합니다. 전체를 한 키에 넣으면 그 키가 손상될 때 기록·카테고리·설정이 한꺼번에 사라집니다. 분할하면 `expenses` 가 손상돼도 `categories` 는 살아남습니다(E-303 이 부분 복구를 하는 근거). 대신 "여러 키에 걸친 쓰기가 중간에 끊길 수 있다"는 위험이 생기는데, 이것은 §3-4 쓰기 순서 규칙으로 다룹니다.

**월별 분할(`jr.v1.expenses.2026-08`)은 채택하지 않았습니다.** 수백~수천 건 규모에서 전체 배열 직렬화 비용이 문제가 되지 않고(§4-4 산정), 월 경계에 걸친 수정(날짜를 다른 달로 바꾸는 F-02)이 두 키에 걸친 트랜잭션이 되어 원자성이 깨지기 때문입니다.

### 3-2. 스키마 버전

버전을 **두 곳**에 둡니다. 역할이 다릅니다.

| 위치 | 값 | 역할 |
|---|---|---|
| 키 접두사 `jr.v1.` | `v1` | **메이저 격리.** v2 가 나와도 v1 키를 지우지 않고 남겨 두어, 마이그레이션 실패 시 되돌릴 수 있습니다 |
| `jr.v1.meta.schema` | `1` (정수) | **마이너 검증.** 읽은 데이터가 이 코드가 이해하는 형태인지 판정 |

읽기 시 판정:

| 조건 | 동작 |
|---|---|
| `meta` 없음 | 신규 설치로 간주. 기본 카테고리 8종 시드 후 `meta` 생성 |
| `meta.appId !== 'jr-expense'` | 다른 앱이 같은 키를 쓴 것으로 간주. E-302 경로로 보관 후 신규 설치 처리 |
| `meta.schema === 1` | 정상 |
| `meta.schema > 1` | 상위 버전이 만든 데이터. **읽지 않고** E-307 으로 중단(덮어쓰면 상위 버전 데이터가 파괴됩니다) |
| `meta.schema < 1` 또는 정수 아님 | E-302 경로 |

### 3-4. 쓰기 순서 규칙 (여러 키에 걸친 변경의 원자성)

localStorage 의 `setItem` 은 개별 호출 단위로는 원자적입니다(실패하면 기존 값이 그대로 남습니다). 하지만 여러 키를 연달아 쓰는 도중 예외가 나면 키 사이에 불일치가 생깁니다. 따라서 **순서를 고정**합니다.

```
1. 새 상태를 메모리에서 전부 만든다 (여기서 실패하면 저장소를 건드리지 않았으므로 무해)
2. 전부 JSON.stringify 한다 (여기서 실패해도 저장소 무해)
3. 데이터 키를 쓴다:  expenses -> categories -> settings
4. 백업본을 쓴다:     expenses.bak -> categories.bak   (이전 값으로)
5. 마지막에 meta 를 쓴다 (lastWriteAt, writeCount 갱신)
```

**`meta` 를 마지막에 쓰는 것이 핵심입니다.** 3~4 단계 도중 중단되면 `meta.lastWriteAt` 이 갱신되지 않으므로, 다음 로드에서 "쓰기가 완료되지 않은 상태"임을 감지할 수 있습니다. 감지 방법은 §7-3 E-301 절차에 있습니다.

4단계(백업본)가 용량 부족으로 실패해도 **3단계는 이미 성공했으므로 데이터는 안전**합니다. 이 경우 백업본을 삭제하고 T 슬롯 E-204 를 표시합니다. 백업이 없는 상태로 계속 동작합니다.

3단계가 실패하면 **메모리 상태를 변경 전으로 되돌리고**(`JR.model` 이 변경 전 스냅샷을 들고 있습니다) E-202 를 반환합니다. 저장소의 기존 값은 `setItem` 실패로 그대로 남아 있으므로 훼손되지 않습니다.

### 3-5. 용량 산정과 임계값

| 항목 | 값 | 근거 |
|---|---|---|
| 기록 1건 직렬화 크기 | 약 110~150 문자 (메모 길이에 따라 최대 +100) | §3-3 예시 실측 |
| 1,000건 | 약 130,000 문자 | 110~150 의 중앙값 130 × 1000 |
| 1,000건 + 백업본 | 약 260,000 문자 | 2배 |
| `JR.store.LIMIT_CHARS` | `2500000` (상수) | **확인 필요-6.** Chromium 계열의 통상 상한이 UTF-16 문자 기준 약 5M 이라고 알려져 있으나 `file://` origin 에서의 실제 값을 제가 검증할 수 없어 **보수적으로 절반**을 잡았습니다 |
| E-203 경고 임계 | 사용률 80% (2,000,000 문자) | 사용자가 내보내기로 대피할 시간을 확보 |
| E-202 발생 지점 | 브라우저가 `QuotaExceededError` 를 던지는 시점 | 상수와 무관하게 실제 예외로 감지 |

사용량 계산은 추정이 아니라 실제 문자열 길이로 합니다.

```js
JR.store.usage = function () {
  var used = 0, i, k;
  for (i = 0; i < localStorage.length; i++) {
    k = localStorage.key(i);
    if (k.indexOf('jr.') !== 0) continue;          // 우리 키만 센다
    used += k.length + (localStorage.getItem(k) || '').length;
  }
  return { ok: true, data: {
    usedChars: used,
    limitChars: JR.store.LIMIT_CHARS,
    ratio: used / JR.store.LIMIT_CHARS
  }};
};
```

**결론: 이 앱의 현실적 사용량(수백~수천 건)은 상한의 10% 안쪽입니다.** 용량 초과는 정상 사용으로는 도달하기 어렵고, 다른 사이트가 같은 `file://` origin 을 공유하거나 손상본 보관이 누적된 경우에 발생합니다. 그래도 E-202 는 필수로 구현합니다.

## 4. 정렬 규칙과 집계 로직

### 4-1. 목록 정렬 (F-04) — 결정적 전순서

비결정적 정렬은 새로고침마다 목록 순서가 바뀌는 버그가 됩니다. 아래 비교자는 **어떤 두 기록에 대해서도 0을 반환하지 않으므로**(`id` 가 유일하므로) `Array.prototype.sort` 의 안정성 보장 여부와 무관하게 항상 같은 결과를 냅니다.

```js
function compareExpenseDesc(a, b) {
  if (a.date !== b.date) return a.date < b.date ? 1 : -1;              // 1) 날짜 내림차순
  if (a.createdAt !== b.createdAt) return b.createdAt - a.createdAt;   // 2) 생성 역순
  return a.id < b.id ? 1 : a.id > b.id ? -1 : 0;                       // 3) id 내림차순 (최종)
}
```

| 순위 | 기준 | 방향 | 왜 이것인가 |
|---|---|---|---|
| 1 | `date` | 내림차순 | 분배안 F-04 명시. `YYYY-MM-DD` 는 고정폭 0패딩이라 문자열 비교가 곧 날짜 비교입니다 |
| 2 | `createdAt` | 내림차순 | "같은 날짜면 생성 역순" (F-04). 나중에 적은 것이 위 |
| 3 | `id` | 내림차순 | `createdAt` 이 같은 밀리초일 수 있습니다. `id` 안의 `_seq` 가 세션 내 단조 증가하므로 생성 순서와 일치합니다 |

**`date` 비교에 `new Date(a.date) - new Date(b.date)` 를 쓰지 마십시오.** `new Date('2026-08-11')` 은 UTC 자정으로 해석되어 로컬 타임존에서 하루 밀립니다. 문자열 비교만 씁니다.

**`localeCompare` 사용 금지.** 로케일에 따라 결과가 달라져 결정성이 깨집니다. 위 코드처럼 `<` / `>` 만 씁니다.

### 4-2. 카테고리 정렬

`order` 오름차순 단일 기준. `order` 는 0..n-1 연속 정수이며 중복이 없도록 유지하므로 tie 가 발생하지 않습니다.

| 시점 | `order` 처리 |
|---|---|
| 추가 | `현재 최대 order + 1`. 목록이 비었으면 0 |
| 이름 변경 | 변경하지 않음 |
| 삭제 | 삭제 후 남은 항목을 기존 `order` 오름차순으로 정렬해 0..n-1 재부여 |
| 가져오기 | 파일의 `order` 값을 **무시**하고 배열 등장 순서대로 0..n-1 재부여 (조작된 파일 방어) |
| 손상 복구 | `order` 가 정수가 아니거나 중복이면 `name` 오름차순(코드포인트)으로 재부여 |

### 4-3. 집계 — 월 총합과 카테고리별 합계 (F-06)

**월 필터**: `expense.date.slice(0, 7) === yyyymm`. `Date` 파싱을 하지 않습니다.

**합계 정확성**: `amount` 는 전부 정수이고 상한이 999,999,999 입니다. `Number.MAX_SAFE_INTEGER`(9,007,199,254,740,991)에 도달하려면 상한 금액 기록이 900만 건 넘게 필요합니다. localStorage 용량이 먼저 터지므로 **오버플로는 발생할 수 없습니다.** 부동소수점 오차도 정수 덧셈에서는 발생하지 않습니다.

**비율 계산 — 최대잔여법(Largest Remainder)**. 단순 반올림은 합이 99% 또는 101% 가 됩니다. 아래는 합이 **항상 정확히 100** 이 되는 순수 함수입니다.

```js
// amounts: 0보다 큰 정수 배열, 이미 §4-3-1 순서로 정렬되어 있어야 함
// total: amounts 의 합
// 반환: 같은 길이의 정수 배열, 합 === 100 (total > 0 인 경우)
JR.stats.allocatePercents = function (amounts, total) {
  var n = amounts.length, out = new Array(n), rem = [], i, floorSum = 0, exact;
  if (!total || total <= 0 || n === 0) {
    for (i = 0; i < n; i++) out[i] = 0;
    return out;
  }
  for (i = 0; i < n; i++) {
    exact = amounts[i] * 100 / total;
    out[i] = Math.floor(exact);
    floorSum += out[i];
    rem.push({ i: i, r: exact - out[i], a: amounts[i] });
  }
  var deficit = 100 - floorSum;                  // 0 <= deficit < n 이 보장됨
  rem.sort(function (x, y) {
    if (y.r !== x.r) return y.r > x.r ? 1 : -1;  // 1) 소수부 큰 순
    if (y.a !== x.a) return y.a - x.a;           // 2) 금액 큰 순
    return x.i - y.i;                            // 3) 입력 순서 (최종·결정적)
  });
  for (i = 0; i < deficit; i++) out[rem[i].i] += 1;
  return out;
};
```

**검산 예시** — 3개 카테고리, 총액 10,000원

| 카테고리 | 금액 | 정확 % | `floor` | 소수부 | 보정 | 최종 % |
|---|---|---|---|---|---|---|
| 식비 | 3,334 | 33.34 | 33 | 0.34 | +1 | **34** |
| 교통 | 3,333 | 33.33 | 33 | 0.33 | +1 | **34** |
| 기타 | 3,333 | 33.33 | 33 | 0.33 | — | **33** |
| 합 | 10,000 | 100.00 | 99 | — | +1 이 2회? | **101** |

위 표가 틀렸다는 것을 확인하십시오 — `floorSum` 은 99 이므로 `deficit` 은 **1** 이고, 보정은 **한 번만** 일어납니다. 소수부 0.34 인 식비가 34%, 나머지 둘은 33% 로 합 100 입니다. 표를 바로잡아 다시 씁니다.

| 카테고리 | 금액 | 정확 % | `floor` | 소수부 | 보정 | 최종 % |
|---|---|---|---|---|---|---|
| 식비 | 3,334 | 33.34 | 33 | 0.34 | +1 | **34** |
| 교통 | 3,333 | 33.33 | 33 | 0.33 | — | **33** |
| 기타 | 3,333 | 33.33 | 33 | 0.33 | — | **33** |
| 합 | 10,000 | 100.00 | 99 (`deficit`=1) | — | 1회 | **100** |

교통과 기타는 소수부가 동일합니다. 이때 2번 기준(금액)도 같으므로 3번 기준(입력 순서)이 승부를 가릅니다. **입력 순서가 결정적이어야 하는 이유가 여기 있습니다** — §4-3-1 이 그것을 보장합니다.

#### 4-3-1. 집계 결과 항목의 정렬 (`allocatePercents` 호출 전에 확정)

```js
function compareStatItem(a, b) {
  if (a.amount !== b.amount) return b.amount - a.amount;               // 1) 금액 내림차순
  if (a.categoryName !== b.categoryName)                                // 2) 이름 오름차순(코드포인트)
    return a.categoryName < b.categoryName ? -1 : 1;
  return a.categoryId < b.categoryId ? -1 : 1;                          // 3) id 오름차순 (최종)
}
```

한글 완성형(U+AC00~U+D7A3)은 코드포인트 순서가 가나다 순과 일치하므로 별도 처리가 필요 없습니다. `__deleted__` 항목은 **정렬에 참여하되 항상 마지막**에 오도록 강제합니다(금액이 크더라도). 사용자가 정상 카테고리를 먼저 보게 하기 위함입니다.

#### 4-3-2. 집계 경계 규칙

| 상황 | 동작 |
|---|---|
| 해당 월 기록 0건 | `{total:0, count:0, items:[]}`. 오류가 아닙니다. 빈 상태 문구는 `ux-designer` 영역 |
| 합계 0원인 카테고리 | `items` 에서 **제외**. `amount >= 1` 제약상 발생하지 않지만 손상 데이터 방어로 명시 |
| 기록이 있는 카테고리가 1개뿐 | `percent` 는 100. `deficit` 은 0 |
| `percent` 가 0 인 항목 | 발생합니다(예: 총액 1,000,000원 중 3,000원 = 0.3%). **항목을 숨기지 않습니다.** `amount` 는 정확한 값이므로 금액은 표시되고 비율만 0% 입니다. 막대 최소 표시 규칙은 `ux-designer` 영역 |
| dangling `categoryId` | `__deleted__` 단일 항목으로 합산, `isDeletedCategory:true` |

### 4-4. 수백~수천 건 규모에서의 연산 방식

| 연산 | 복잡도 | 방식 |
|---|---|---|
| 로드 시 `monthIndex` 구축 | O(n) 1회 | `{'YYYY-MM': [배열인덱스,...]}`. `date.slice(0,7)` 을 키로 단일 순회 누산 |
| 월 목록 조회 | O(m log m) | m = 해당 월 건수. `monthIndex` 로 후보를 뽑은 뒤 §4-1 비교자로 정렬 |
| 월 총합 | O(m) | 단일 순회 덧셈 |
| 카테고리별 집계 | O(m) + O(k log k) | k ≤ 21 (카테고리 20 + `__deleted__`). 해시 누산 후 정렬 |
| 사용 가능한 월 목록 | O(1) | `monthIndex` 의 키를 내림차순 정렬. 키 수는 기록 기간의 개월 수 |

**캐시 정책**

- `JR.stats` 는 `statsCache[yyyymm]` 에 `byCategory` 결과를 보관합니다.
- **무효화 트리거**: `JR.model` 의 모든 쓰기 함수(`addExpense`·`updateExpense`·`deleteExpense`·`addCategory`·`renameCategory`·`deleteCategory`·`wipeAll`·`applyImport`)가 성공하면 `JR.stats.invalidate()` 를 **호출자가 아니라 `JR.model` 이 직접** 호출합니다. UI 가 잊어버릴 여지를 없앱니다.
- 부분 무효화를 하지 않습니다. 캐시 항목 수가 많아야 수십 개(개월 수)이고 재계산이 O(m) 이라 부분 무효화의 복잡도가 이득보다 큽니다.
- `monthIndex` 도 같은 시점에 통째로 재구축합니다.

**성능 목표와 검증 책임**: 1,000건 기준 로드 후 첫 렌더까지의 데이터 계층 연산이 단일 프레임(약 16ms) 안에 끝나는 것을 목표로 잡습니다. 다만 이것은 제가 실행해 본 수치가 아니라 복잡도로부터의 기대치입니다. ④ 개발본부가 1,000건·5,000건 더미 데이터로 실측하십시오(§9 확인필요-11). 실측 결과가 목표를 넘으면 그때 월별 키 분할을 재검토하되, **미리 최적화하지 않습니다.**

### 4-5. 금액 표시 포맷

`Intl.NumberFormat` 가용성을 `file://` 에서 단정할 수 없고, 있더라도 로케일에 따라 구분자가 달라질 수 있습니다. 자체 구현을 씁니다.

```js
JR.stats.formatAmount = function (n) {          // 12500 -> "12,500"
  if (typeof n !== 'number' || !isFinite(n)) return '0';
  var neg = n < 0, s = String(Math.abs(Math.trunc(n))), out = '', i, c = 0;
  for (i = s.length - 1; i >= 0; i--) {
    out = s.charAt(i) + out;
    if (++c % 3 === 0 && i > 0) out = ',' + out;
  }
  return (neg ? '-' : '') + out;
};
```

반환값에 **단위("원")를 붙이지 않습니다.** 단위 표기는 화면 문구이므로 `ux-designer` 영역입니다. 이 함수는 숫자 부분만 만듭니다.

### 4-6. 글자 수 세기 (이모지 대응)

`str.length` 는 UTF-16 코드 유닛 수입니다. 이모지 U+1F600 은 2로 세어져, 사용자가 이모지 3개만 넣어도 "6자"가 됩니다. **코드포인트 단위로 셉니다.**

```js
JR.model.countChars = function (s) {
  if (typeof s !== 'string') return 0;
  if (typeof Array.from === 'function') return Array.from(s).length;
  var n = 0, i = 0, c, d;
  while (i < s.length) {
    c = s.charCodeAt(i);
    if (c >= 0xD800 && c <= 0xDBFF && i + 1 < s.length) {
      d = s.charCodeAt(i + 1);
      if (d >= 0xDC00 && d <= 0xDFFF) { i += 2; n++; continue; }
    }
    i++; n++;
  }
  return n;
};
```

**문서화된 한계 — 숨기지 않고 명시합니다.** ZWJ(U+200D)로 결합된 이모지(가족 이모지 등)는 코드포인트 여러 개로 세어집니다. 가족 이모지 1개가 7자로 계산될 수 있습니다. `Intl.Segmenter`(grapheme 단위)를 쓰면 정확하지만 가용성을 `file://` 에서 확인할 수 없고 구형 브라우저에 없습니다. 이 한계는 **E-121 전용 문구**로 사용자에게 설명합니다(§7-1).

`maxlength` 속성은 UTF-16 기준이라 위 규칙과 어긋납니다. **HTML `maxlength` 를 신뢰하지 말고** `input` 이벤트에서 `countChars` 로 재검사하십시오.

## 5. 모듈 인터페이스

### 5-0. 이 장을 읽는 ④ 개발본부에게

이 장은 **두 개발자가 서로의 코드를 보지 못한다는 전제**로 씁니다. 아래에 적힌 함수명·인자 개수·인자 순서·반환 객체의 키 이름은 **계약**입니다. 구현 내부는 자유지만 시그니처와 반환 형태를 바꾸면 다른 개발자의 코드가 깨집니다. 바꿔야 한다고 판단되면 고치지 말고 `ai-team/questions.md` 에 Q 를 남기십시오.

### 5-1. 스크립트 로드 순서와 의존 방향

ES 모듈을 쓸 수 없으므로(P-4) `index.html` 에 `<script>` 를 **아래 순서 그대로** 나열합니다. 순서를 바꾸면 로드 시점에 `JR.err` 등이 없어 `TypeError` 가 납니다.

```html
<script src="js/err.js"></script>     <!-- 1 -->
<script src="js/store.js"></script>   <!-- 2 -->
<script src="js/model.js"></script>   <!-- 3 -->
<script src="js/stats.js"></script>   <!-- 4 -->
<script src="js/io.js"></script>      <!-- 5 -->
<script src="js/ui.js"></script>      <!-- 6 -->
<script src="js/boot.js"></script>    <!-- 7 : 부팅 시퀀스(§5-9)만 들어 있음 -->
```

각 파일의 첫 줄은 다음과 같습니다. 전역은 `JR` 하나뿐이며 다른 전역 변수를 만들지 않습니다.

```js
var JR = JR || {};
JR.store = (function () { 'use strict'; /* ... */ return { /* 공개 API */ }; })();
```

**의존 방향 (화살표는 "호출한다")**

```
        err  ←  store  ←  model  ←  stats
         ↑        ↑         ↑   ↖     ↑
         └────────┴─────────┴────  io ┘
                        ↑
                       ui  (모든 하위 모듈을 읽지만, 하위 모듈은 ui 를 호출하지 않는다)
```

| 모듈 | 호출해도 되는 것 | 절대 호출하면 안 되는 것 |
|---|---|---|
| `JR.err` | 없음 (순수) | 전부 |
| `JR.store` | `JR.err` | `JR.model` · `JR.stats` · `JR.io` · `JR.ui` |
| `JR.model` | `JR.err` · `JR.store` · **`JR.stats.invalidate` (아래 예외 1건)** | `JR.io` · `JR.ui` |
| `JR.stats` | `JR.err` · `JR.model` (읽기 전용 함수만) | `JR.store` · `JR.io` · `JR.ui` |
| `JR.io` | `JR.err` · `JR.store` · `JR.model` | `JR.ui` |
| `JR.ui` | 전부 | — |

**예외 1건 (§4-4 캐시 정책의 근거)**: `JR.model` 의 쓰기 함수는 성공 직후 `JR.stats.invalidate()` 를 직접 호출합니다. 이것이 유일하게 허용된 역방향 호출입니다. 로드 순서상 `stats.js` 는 `model.js` 뒤에 오므로, `model.js` 안에서는 **호출 시점에 존재 여부를 확인**해야 합니다.

```js
function notifyChange(kind) {                       // kind: 'expense' | 'category' | 'settings' | 'bulk'
  if (JR.stats && typeof JR.stats.invalidate === 'function') JR.stats.invalidate();
  var i;
  for (i = 0; i < subscribers.length; i++) {        // JR.model.subscribe 로 등록된 함수들
    try { subscribers[i](kind); } catch (e) { JR.err.log('E-501', e); }
  }
}
```

`JR.ui` 는 `subscribe` 로만 변경을 통지받습니다. **하위 모듈이 `JR.ui` 를 직접 부르는 코드를 쓰지 마십시오.**

### 5-2. 공통 반환 규약 (전 모듈 동일)

```
성공: { ok: true,  data: <객체> }
실패: { ok: false, code: 'E-xxx', data: <객체> }
```

| 규칙 | 내용 |
|---|---|
| R-1 | `ok` 는 항상 boolean 리터럴 `true`/`false` 입니다. truthy 값으로 대신하지 않습니다 |
| R-2 | 성공 시 `data` 는 **항상 객체**입니다. 값 하나를 돌려줄 때도 `{count: 3}` 처럼 이름을 붙입니다. 배열이나 원시값을 그대로 반환하지 않습니다 |
| R-3 | 실패 시 `code` 는 §7 표에 있는 코드여야 합니다. 표에 없는 코드를 만들지 않습니다 |
| R-4 | 실패 시에도 `data` 는 객체입니다(비면 `{}`). 문구에 채울 값은 `data.params` 에 넣습니다 — 예: `{ok:false, code:'E-116', data:{params:{name:'식비'}}}` |
| R-5 | **예외를 던지지 않습니다.** 모든 공개 함수는 내부 `try/catch` 로 감싸고 실패를 반환값으로 표현합니다. 예상 못 한 예외는 `E-501` 로 변환합니다 |
| R-6 | **순수 계산 함수 9개는 예외**입니다 — `JR.model` 의 `today` · `minDate` · `maxDate` · `countChars` · `normName` · `shiftMonth` · `monthRange`, `JR.stats` 의 `allocatePercents` · `formatAmount`. 이들은 실패할 수 없으므로 원시값/배열/평범한 객체를 그대로 반환합니다(§5-4-2·§5-5 에 표시) |
| R-6-1 | **상태 조회 함수 3개도 예외**입니다 — `JR.store.mode()` · `JR.model.isReady()` · `JR.model.isNoticeDismissed()`. 렌더 루프에서 매번 불리는 판정용이라 `ok` 로 감싸면 호출부가 매번 두 겹을 벗겨야 합니다. **이 12개 외에는 전부 R-1~R-5 를 따릅니다.** 목록에 함수를 추가하지 마십시오 |
| R-7 | 반환된 객체·배열은 **읽기 전용으로 취급**합니다. `JR.model.getExpenses()` 가 돌려준 배열의 원소는 내부 객체와 같은 참조입니다. UI 가 `e.amount = 0` 처럼 직접 대입하면 다음 저장에 그대로 반영되어 데이터가 오염됩니다. 값을 바꾸려면 반드시 `updateExpense` 를 쓰십시오 |

**여러 필드가 동시에 틀렸을 때** — 검증 함수는 **모든 오류를 모아** 반환합니다. UI 가 인라인 오류를 한 번에 다 띄울 수 있어야 하기 때문입니다.

```js
{ ok: false,
  code: 'E-101',                                     // 첫 번째 오류(대표 코드)
  data: { errors: [ { field: 'amount',     code: 'E-101', params: {} },
                    { field: 'categoryId', code: 'E-112', params: {} } ] } }
```

`field` 값은 `'date' | 'amount' | 'categoryId' | 'memo' | 'name'` 다섯 가지뿐입니다. UI 는 이 값으로 어느 입력란 아래에 붙일지 결정합니다.

### 5-3. `JR.store` — localStorage 입출력 (의존: `JR.err`)

이 모듈은 **`jr.` 로 시작하는 키만** 다룹니다. 다른 키를 읽거나 쓰지 않습니다. `Expense`·`Category` 같은 도메인 개념을 모릅니다(문자열과 JSON 값만 압니다).

| `mode()` | `JR.store.mode()` | `'persist' \| 'memory'` (원시값, R-6 예외 아님 — 아래 주 참고) | |

| `deleteCategory(id)` | `id: string` | `{ok:true, data:{orphanedExpenseCount: number}}` / `{ok:false, code:'E-118'\|'E-124'}` |

`getCategoryName` 은 존재하지 않는 id 에 대해 **실패하지 않고** `{name:'미분류(삭제된 카테고리)', isDeletedCategory:true}` 를 반환합니다. 이 라벨 문자열은 화면설계 §0-4 가 확정한 값을 그대로 씁니다(§2-7 주1 의 Q-007 은 이 값으로 해소된 것으로 봅니다 — 최종 확인은 `product-planner` 통합 시).

`deleteCategory` 는 **삭제 전에** 영향 건수를 세어 반환합니다. UX 의 확인 대화상자는 삭제 **전에** 건수를 보여줘야 하므로, 대화상자를 띄우기 전에는 `countByCategory(id)` 를 쓰고, 대화상자 확정 후 `deleteCategory(id)` 를 부르십시오. 두 값은 같습니다.

### 5-6. `JR.io` — 내보내기 / 가져오기 (의존: `JR.err` · `JR.store` · `JR.model`)

#### 5-6-1. 내보내기 파일 스키마 (F-08)

```json
{
  "app": "jr-expense",
  "kind": "backup",
  "schema": 1,
  "exportedAt": 1786598400123,
  "exportedDate": "2026-08-11",
  "counts": { "expenses": 3, "categories": 9 },
  "data": {
    "expenses": [
      {"id":"e_ldk2h9_1_4m2x","date":"2026-08-11","amount":12500,"categoryId":"c_d01","memo":"점심 김치찌개","createdAt":1786598400123}

      {"id":"c_d01","name":"식비","order":0,"isDefault":true}
    ],
    "settings": { "selectedMonth": "2026-08" }
  }

```

| 필드 | 규칙 |
|---|---|
| `app` | 문자열 `"jr-expense"` 고정. **이 값이 다르면 가져오기를 거부**합니다(E-405) |
| `kind` | 문자열 `"backup"` 고정. 장래에 다른 종류의 파일이 생겨도 구분되게 둡니다 |
| `schema` | 정수 `1`. `jr.v1.meta.schema` 와 같은 값 |
| `exportedAt` | `Date.now()` 정수. 표시용 아님(파일 비교용) |
| `exportedDate` | `JR.model.today()` 결과. 사람이 파일을 열어 봤을 때 읽히는 값 |
| `counts` | 검증용 중복 정보. `data.expenses.length` 와 다르면 `E-407` |
| `data.settings` | `selectedMonth` **만** 내보냅니다. `dismissedNotices` 는 기기별 상태이므로 **내보내지도 가져오지도 않습니다** |

들여쓰기 없이 `JSON.stringify(obj)` 로 직렬화합니다(파일 크기 절감). 사람이 읽을 필요가 있으면 브라우저에서 열어 보면 됩니다.

**파일명 규칙**: `jr-backup-YYYY-MM-DD-HHMM.json`
- `YYYY-MM-DD` 는 `JR.model.today()`, `HHMM` 은 로컬 `getHours()`/`getMinutes()` 를 2자리 0패딩.
- 시각까지 넣는 이유: 같은 날 두 번 내보내면 같은 이름이 되어 브라우저 다운로드 폴더에서 `(1)` 이 붙거나 덮어쓰기 확인이 뜹니다. 사용자가 어느 파일이 최신인지 알 수 없게 됩니다.
- 앱 이름(`정레`)을 파일명에 넣지 않습니다. ③ 디자인본부에서 이름이 바뀌면 과거 백업 파일과 접두사가 어긋납니다.

### 5-7. `JR.err` — E-코드와 문구 (의존: 없음)

**문구의 단일 출처는 §7 의 표입니다.** `js/err.js` 의 `MESSAGES` 객체는 §7 표를 그대로 옮겨 적은 것이며, 문구를 바꿔야 하면 §7 을 먼저 고치고 코드를 맞춥니다. 코드에만 있는 문구를 만들지 마십시오.

| 이름 | 시그니처 | 반환 |
|---|---|---|
| `MESSAGES` | 객체 | `{'E-101': {slot:'I', field:'amount', msg:'금액을 입력해 주세요.'}, ...}` |
| `get(code, params)` | `code: string, params: object\|undefined` | `{code, msg, slot, field}` — 없는 코드면 `E-599` 의 내용에 `code` 만 원본으로 채워 반환 |
| `slot(code)` | `code: string` | `'T' \| 'I' \| 'B'` — 없는 코드면 `'T'` |

| `ok(data)` | `data: object` | `{ok:true, data:data\|{}}` |

### 5-8. `JR.ui` — 화면 렌더 (④ 개발본부 구현 영역, 여기서는 호출 규약만)

`JR.ui` 의 내부 구조는 ④ 가 정합니다. 다만 아래 4개 함수는 **하위 모듈의 반환값을 화면에 옮기는 통로**이므로 이름과 인자를 고정합니다. 부팅 코드(`boot.js`)와 화면 코드가 서로 다른 개발자에게 배정될 수 있기 때문입니다.

| 이름 | 시그니처 | 동작 계약 |
|---|---|---|
| `toast(code, params)` | `code: string, params: object\|undefined` | T 슬롯. `JR.err.get` 으로 문구를 만들어 표시. 이미 토스트가 떠 있으면 **교체**(화면설계 §0-2) |
| `inline(field, code, params)` | `field: string, code, params` | I 슬롯. `field` 는 §5-2 의 5종. `code` 가 `null` 이면 그 필드의 인라인 오류를 **지웁니다** |
| `banner(code, params)` | `code, params` | B 슬롯. 같은 코드의 배너가 이미 있으면 다시 만들지 않습니다 |
| `dismissBanner(code)` | `code: string` | 배너 닫기. §7-8 규칙에 따라 `JR.model.dismissNotice` 호출 여부가 갈립니다 |

**슬롯 판정을 UI 가 하지 않습니다.** `JR.err.slot(code)` 이 `'B'` 인데 `JR.ui.toast(code)` 를 부르면 계약 위반입니다. 코드 하나를 받아 알아서 뿌리는 헬퍼를 하나 두는 것을 권합니다.

```js
JR.ui.show = function (code, params, field) {
  var s = JR.err.slot(code);
  if (s === 'I') return JR.ui.inline(field || JR.err.get(code).field, code, params);
  if (s === 'B') return JR.ui.banner(code, params);
  return JR.ui.toast(code, params);
};
```

### 5-9. 부팅 시퀀스 (`boot.js` — 이 순서 그대로)

```
 1. JR.store.init()                     → mode 결정. 실패하지 않음
 2. mode === 'memory' 이면 notices 에 'E-201' 추가
 3. JR.model.init()                     → 저장 데이터 읽기·검증·복구(§6-3)
 4. ok:false (E-307) 이면 → 읽기 전용 모드로 §6-3-5 진입. 5~8 을 건너뛰고 배너만 렌더
 5. JR.store.usage() 로 사용률 확인 → ratio >= 0.8 이면 notices 에 'E-203' 추가
 6. 환경 감지(§6-8) 실행 → 필요 시 notices 에 'E-002' 추가
 7. JR.ui 초기 렌더 (선택된 월 = settings.selectedMonth)
 8. notices 배열을 §7-8 규칙으로 표시
 9. window 이벤트 등록: 'visibilitychange'(§6-8-3) · 'pagehide'(§6-6)
```

1~6 은 **전부 동기**입니다. localStorage 읽기와 `JSON.parse` 뿐이므로 비동기 대기가 없습니다. 화면설계의 "불러오는 중" 상태는 이 구간에 해당하며 한 프레임 안에 끝날 수 있습니다. 그렇더라도 7단계 전에는 상호작용 요소를 렌더하지 않습니다(화면설계 S-01 로딩 상태 규칙).

## 6. 예외 8종 — 감지 · 복구 · 사용자에게 보이는 결과

분배안 §4-2 "이 환경에서 반드시 다뤄야 하는 예외(누락 시 반려)" 8항목을 순서대로 다룹니다. 각 항목은 **어떻게 감지하는가(코드)** · **무엇을 되돌리는가** · **사용자 화면에 무엇이 남는가** 세 가지를 전부 씁니다. 문구 전문과 슬롯은 §7 표에 있습니다.

### 6-1. localStorage 자체가 차단됨 → 메모리 모드 (E-201)

**감지** — 존재 확인만으로는 부족합니다. Safari 사설 창처럼 객체는 있는데 쓰기가 예외를 던지는 경우, 그리고 쓰기는 되는데 값이 남지 않는 경우가 있습니다. 세 가지를 한 번에 봅니다.

```js
function probeStorage() {
  var ls, k = 'jr.__probe';
  try { ls = window.localStorage; }        // 1) getter 접근 자체가 SecurityError 를 던짐
  catch (e) { return false; }
  if (!ls) return false;                   // 2) 객체가 없음
  try {
    ls.setItem(k, '1');
    if (ls.getItem(k) !== '1') { return false; }   // 3) 썼는데 값이 안 남음
    ls.removeItem(k);
    return true;
  } catch (e) { return false; }            // 4) setItem 이 예외(용량 0 포함)
}
```

**복구 동작**

1. `JR.store.MODE = 'memory'`. 내부 `var mem = {}` 를 저장소 대신 사용합니다.
2. `JR.store` 의 모든 함수는 시그니처·반환 형태를 그대로 유지합니다. **상위 모듈은 분기하지 않습니다.**
3. 기본 카테고리 8종을 메모리에 시드합니다. F-01~F-09 전 기능이 정상 동작합니다.
4. `notices` 에 `E-201` 을 넣습니다.
5. 이 모드에서는 `E-202`(용량 초과)·`E-203`(80% 경고)·`E-204`(백업 실패)를 **발생시키지 않습니다.** 메모리에는 상한이 없고, 상한 경고를 띄우면 사용자가 두 개의 다른 문제로 오해합니다.

**사용자에게 보이는 결과**: B 슬롯 배너 `E-201` 이 4개 화면 전부에 상시 노출됩니다. 배너를 닫아도 **다음 화면 진입 시 다시 나타납니다**(원인이 해소되지 않았으므로 — 화면설계 §0-2 규칙과 일치, §7-8 의 "상태형"). 기록 추가·수정·삭제·통계·내보내기는 평소와 똑같이 동작하며, 이 세션 동안 사용자는 기능 제한을 느끼지 않습니다.

**내보내기는 이 모드에서 더 중요해집니다.** 배너 문구가 내보내기를 안내하는 이유입니다.

### 6-2. 용량 초과 (E-202 · E-203 · E-204 · E-205)

**감지 — 예외 이름으로 판정합니다.** 브라우저마다 던지는 것이 다릅니다.

```js
function isQuotaError(e) {
  if (!e) return false;
  return e.name === 'QuotaExceededError' ||
         e.name === 'NS_ERROR_DOM_QUOTA_REACHED' ||   // Firefox
         e.code === 22 || e.code === 1014;            // 구형 DOMException 코드
}
```

**쓰기 후 read-back 검증** — `setItem` 이 조용히 실패하는 환경이 있습니다. `JR.store.setRaw` 는 쓴 직후 되읽어 확인하고, 다르면 `E-205` 를 반환한 뒤 **메모리 모드로 전환**합니다(그 시점부터 §6-1 과 동일한 상태).

```js
ls.setItem(key, value);
if (ls.getItem(key) !== value) { return JR.err.fail('E-205', {}); }
```

**복구 사다리 (`writeAll` 이 `QuotaExceededError` 를 만났을 때 — 위에서부터 순서대로 1회씩 시도)**

| 단계 | 지우는 것 | 사용자가 잃는 것 |
|---|---|---|
| 1 | `jr.v1.corrupt.*` 전부 | 과거 손상 원본 보관본. 이미 복구가 끝난 것이므로 실사용 영향 없음 |
| 2 | `jr.v1.rejected` | 가져오기에서 탈락했던 원본 보관본 |
| 3 | `jr.v1.expenses.bak` · `jr.v1.categories.bak` | 백업본. 다음 손상 시 복구 가능성이 낮아짐 |
| 4 | `jr.v1.draft` | 작성 중이던 초안 |
| 5 | 재시도 실패 | 여기서 멈춥니다. **실제 데이터(`expenses`·`categories`)는 절대 지우지 않습니다** |

5단계까지 실패하면:

1. `JR.model` 이 들고 있던 **변경 전 메모리 스냅샷으로 되돌립니다.** 사용자가 방금 입력한 기록 1건은 사라지고, 그 전까지의 데이터는 화면에도 저장소에도 그대로 남습니다.
2. `{ok:false, code:'E-202'}` 를 반환합니다.
3. 저장소의 기존 값은 `setItem` 이 실패했으므로 훼손되지 않았습니다(§3-4).

**사용자에게 보이는 결과**: B 슬롯 `E-202` 배너 + 그 시도가 실패했다는 사실. 화면의 목록은 저장 시도 **이전** 상태로 보입니다(입력한 기록이 목록에 없습니다). 이것이 "저장된 것처럼 보이는데 사실은 아닌" 상태보다 안전합니다.

**예방**: 부팅 시와 매 `writeAll` 성공 후 `usage().ratio >= 0.8` 이면 `E-203`(B 슬롯)을 띄웁니다. 이 배너는 §7-8 의 "사건형"이라 닫으면 다시 뜨지 않습니다. 단 다음 부팅에서 여전히 80% 이상이면 다시 뜹니다.

**백업본만 실패한 경우**(§3-4 4단계): 데이터는 이미 3단계에서 저장됐으므로 안전합니다. `.bak` 두 개를 삭제하고 `E-204`(T 슬롯)를 알린 뒤 백업 없는 상태로 계속 동작합니다. 저장 자체는 **성공**으로 처리합니다.

### 6-3. 저장된 JSON 이 파싱 불가(손상)

**전체 초기화로 도망가지 않습니다.** 키를 분할해 둔 이유(§3-1)가 여기서 쓰입니다. 손상은 키 단위로 격리되고, 키 안에서도 레코드 단위로 격리됩니다.

#### 6-3-1. 키 단위 복구 절차 (`expenses`·`categories` 각각 독립 수행)

```
1. getRaw(key) → null 이면 정상(신규 설치). 종료
2. JSON.parse 시도
   실패 → quarantine(key, raw) 로 원본 보관 → 3단계
   성공 → 4단계
3. getRaw(key + '.bak') → JSON.parse
   성공 → 이 값을 채택. notices += 'E-303'
   실패/없음 → 해당 키만 초기값 채택 (expenses: [], categories: 기본 8종). notices += 'E-303'
4. 최상위 타입 검사: 배열이 아니면 3단계와 동일 경로. notices += 'E-304'
5. 레코드 단위 검증(§6-3-2) → 유효분만 채택, 탈락분은 jr.v1.rejected 에 보관. notices += 'E-304'
6. 정합성 보정(§6-3-3)
```

**`categories` 가 손상돼도 `expenses` 는 손대지 않습니다.** 카테고리가 기본 8종으로 되돌아가면 기존 기록의 `categoryId` 는 dangling 이 되고, §2-7 규칙에 따라 `미분류(삭제된 카테고리)` 로 표시되며 **금액은 1원도 사라지지 않습니다.**

#### 6-3-2. 레코드 단위 검증 (탈락 조건 — 하나라도 걸리면 그 레코드만 버림)

| 대상 | 탈락 조건 |
|---|---|
| `Expense` | 객체가 아님 / `id` 가 문자열이 아니거나 빈 문자열 / `date` 가 `/^\d{4}-\d{2}-\d{2}$/` 불일치 / `amount` 가 정수가 아님 또는 1 미만 또는 999,999,999 초과 / `categoryId` 가 문자열이 아님 / `createdAt` 이 정수가 아님 |
| `Expense` (보정 가능) | `memo` 가 문자열이 아니면 **탈락시키지 않고** `''` 로 보정. `createdAt` 이 없거나 정수가 아니면 `0` 으로 보정(정렬 최하위) |
| `Category` | 객체가 아님 / `id` 가 문자열이 아니거나 빈 문자열 / `name` 이 문자열이 아니거나 코드포인트 0자 또는 12자 초과 |
| `Category` (보정 가능) | `order` 가 정수가 아니면 §6-3-3 에서 재부여. `isDefault` 가 boolean 이 아니면 `false` |
| 공통 | `id` 중복 — **뒤에 나온 것을 버립니다**(먼저 나온 것을 남김) |

탈락분은 `jr.v1.rejected` 에 `{at: epochMs, source:'load'|'import', items:[...]}` 로 보관하되 **최대 100건**만 담습니다. 초과분은 담지 않습니다(용량 보호). 보관 자체가 실패하면 `E-308` 을 `notices` 에 넣고 진행합니다.

#### 6-3-3. 정합성 보정 (검증 통과 후)

| 조건 | 보정 | 코드 |
|---|---|---|
| 카테고리가 0개 | 기본 8종을 시드 | `E-305` |
| `order` 가 정수가 아니거나 중복이거나 0..n-1 연속이 아님 | `name` 코드포인트 오름차순으로 0..n-1 재부여(§4-2) | `E-306` |
| `settings` 파싱 실패 또는 `selectedMonth` 가 `YYYY-MM` 형식이 아님 | 이번 달로 되돌림. `dismissedNotices` 는 `[]` | `E-309` |
| `settings.selectedMonth` 가 허용 범위 밖 | 가장 가까운 경계값으로 보정 | 알리지 않음(§7-9) |

#### 6-3-4. 쓰기가 완료되지 않은 상태 감지 (E-301)

`meta` 를 마지막에 쓰기 때문에(§3-4), 데이터 키는 갱신됐는데 `meta` 가 안 갱신된 상태가 존재할 수 있습니다. **새 필드를 추가하지 않고** 기존 필드만으로 감지합니다.

```js
var maxCreated = 0, i;
for (i = 0; i < expenses.length; i++) {
  if (expenses[i].createdAt > maxCreated) maxCreated = expenses[i].createdAt;
}
if (meta && maxCreated > meta.lastWriteAt) { /* E-301 */ }
```

**복구 동작**: 데이터 키를 신뢰합니다(`setItem` 은 개별 호출 단위로 원자적이므로 그 자체는 온전합니다). `.bak` 두 개를 현재 값으로 다시 만들고 `meta.lastWriteAt` 을 `Date.now()` 로 갱신합니다. 사용자 데이터는 **변하지 않습니다.** `notices += 'E-301'`.

**이 감지 방법의 한계를 명시합니다.** 삭제만 수행하던 중 끊긴 경우(새 `createdAt` 이 생기지 않음)는 감지되지 않습니다. 다만 그 경우에도 각 키의 값은 개별적으로 온전하므로 데이터 정합성 문제는 발생하지 않고, `.bak` 이 한 세대 낡을 뿐입니다. **감지되지 않는 경우가 있다는 사실을 숨기지 않고 남깁니다.**

#### 6-3-5. 상위 스키마 버전 (E-307) — 읽기 전용 모드

`meta.schema > 1` 이면 **읽지도 쓰지도 않습니다.** 상위 버전이 만든 데이터를 이 버전이 해석하면 필드를 잃고, 그 상태로 저장하면 상위 버전 데이터가 파괴됩니다.

| 항목 | 동작 |
|---|---|
| 화면 | S-01 을 빈 상태로 렌더하고 B 슬롯 `E-307` 배너 고정. **이 배너는 닫을 수 없습니다**(닫으면 사용자가 빈 앱을 새 설치로 오해해 기록을 다시 입력합니다) |
| 쓰기 | `JR.model` 의 모든 쓰기 함수가 `{ok:false, code:'E-307'}` 을 즉시 반환 |
| 지출 추가 버튼 | UI 가 비활성화. (화면설계에 이 조건이 없으므로 §8 Q-011 로 남깁니다) |
| 유일한 탈출구 | 사용자가 브라우저 데이터를 지우거나 상위 버전 앱을 다시 여는 것. 앱이 임의로 지우지 않습니다 |

### 6-4. 가져온 파일이 이 앱의 JSON 이 아님 (E-404 ~ E-411)

**대원칙: 검증이 전부 끝나기 전에는 저장소를 한 글자도 건드리지 않습니다.** 파싱·검증은 전부 메모리에서 끝냅니다.

#### 6-4-1. 검증 순서 (앞 단계가 실패하면 뒤로 가지 않음)

| # | 검사 | 실패 코드 |
|---|---|---|
| V-1 | 파일 선택 자체가 취소됨(`files.length === 0`) | 오류 아님. 아무 것도 하지 않음 |
| V-2 | `FileReader` 가 `onerror` 를 부름(읽기 권한 거부·파일 삭제됨·잠김) | `E-403` |
| V-3 | 파일 문자 수 > `MAX_IMPORT_CHARS`(4,000,000) | `E-408` |
| V-4 | `JSON.parse` 실패 | `E-404` |
| V-5 | 최상위가 객체가 아님 / `app !== 'jr-expense'` / `kind !== 'backup'` | `E-405` |
| V-6 | `schema` 가 정수가 아님 / `schema > 1` | `E-406` |
| V-7 | `data` 가 객체가 아님 / `data.expenses` 또는 `data.categories` 가 배열이 아님 | `E-407` |
| V-8 | 레코드 단위 검증(§6-3-2, `source:'import'`) 후 **유효 카테고리가 0개** | `E-407` |
| V-9 | `counts.expenses` 가 정수인데 `data.expenses.length` 와 다름 | `E-407` |
| V-10 | 유효 카테고리가 20개 초과 | 초과분을 **뒤에서부터 버립니다**. `rejectedCategoryCount` 에 반영. 거부하지 않음 |
| V-11 | 카테고리 이름이 §2-6 기준 중복 | 뒤에 나온 것을 버림. `rejectedCategoryCount` 에 반영 |
| V-12 | 전부 통과 | `{ok:true, data:{payload, summary}}` |

V-1~V-9 실패 시 화면은 S-04 에 그대로 머물고 **기존 데이터는 손도 대지 않습니다**(화면설계 S-04 "형식이 이 앱의 데이터가 아니면 T 슬롯 오류로 종료, 대화상자 없이 끝"과 일치).

`order` 는 파일 값을 무시하고 배열 등장 순서대로 0..n-1 을 재부여합니다(§4-2). `settings.selectedMonth` 는 형식이 맞을 때만 수용하고, `dismissedNotices` 는 파일에 있어도 **버립니다.**

#### 6-4-2. 적용(트랜잭션) 절차 — `applyImport`

```
1. JR.store.snapshot()  → 현재 jr.v1.* 전체를 문자열 맵으로 확보
2. 그 스냅샷을 jr.v1.rollback 에 기록          (실패 시: E-410 반환, 여기서 중단. 데이터 무변경)
3. JR.model.replaceAll(payload.data) 호출      (내부에서 §3-4 쓰기 순서 수행)
   실패 → 4단계
   성공 → 5단계
4. JR.store.restore(스냅샷) 으로 되돌림
   성공 → {ok:false, code:'E-410'}
   실패 → {ok:false, code:'E-411'}  (jr.v1.rollback 은 지우지 않고 남깁니다)
5. jr.v1.rollback 삭제 → JR.stats.invalidate() → {ok:true, data:{...}}
```

부팅 시 `jr.v1.rollback` 이 남아 있으면 3~4단계 사이에서 앱이 죽은 것입니다. 이때 `JR.model.init()` 은 **자동으로 `restore` 를 1회 시도**하고, 성공하면 `notices += 'E-410'`, 실패하면 `notices += 'E-411'` 을 넣습니다.

**사용자에게 보이는 결과**

| 상황 | 결과 |
|---|---|
| V-1~V-9 실패 | T 슬롯 오류 1건. S-04 유지. 기존 기록 그대로 |
| V-10·V-11 로 일부 버림 + 성공 | 화면설계대로 S-01 이동 + T 슬롯 `가져오기를 완료했습니다`(UX 문구) **직후** T 슬롯 `E-409` 로 교체 표시. 토스트는 마지막 것으로 교체되므로(화면설계 §0-2) **성공 토스트를 생략하고 `E-409` 만 표시**합니다 |
| `E-410` | B 슬롯 배너. 데이터는 가져오기 **이전 상태**로 완전히 복구됨 |
| `E-411` | B 슬롯 배너(닫을 수 없음). 데이터가 중간 상태일 수 있음. 배너 문구가 내보내기 대신 **재시작**을 안내합니다(재시작 시 자동 복구가 한 번 더 시도됩니다) |

### 6-5. 저장 버튼 중복 클릭 (E-601)

**이 앱의 모든 저장 경로는 동기입니다.** localStorage 쓰기에는 대기가 없으므로 "저장 중에 또 눌리는" 재진입은 발생하지 않습니다. 실제 사고는 다른 곳에서 납니다 — **첫 번째 클릭 처리가 끝나고 화면이 바뀌기 전에 두 번째 클릭 이벤트가 큐에 들어와 있는 경우**입니다. 더블탭, 터치와 마우스 이벤트의 중복 발생(`touchend` + `click`), 엔터 키 홀드가 여기에 해당합니다.

**감지·차단 — UI 계층의 잠금 하나로 단일화합니다.** `JR.ui` 에 §5-8 의 4개에 이어 **다섯 번째 고정 함수**를 둡니다.

```js
// 잠금 획득: 성공하면 true, 이미 잠겨 있으면 false
JR.ui.lock = function (actionKey) { /* actionKey: 'save' | 'delete' | 'export' | 'import' | 'wipe' | 'category-add' */ };
JR.ui.unlock = function (actionKey) { };
```

모든 파괴적/생성적 동작의 핸들러는 이 형태를 따릅니다.

```js
function onSaveClick() {
  if (!JR.ui.lock('save')) { JR.ui.toast('E-601'); return; }   // 두 번째 클릭
  var r = JR.model.addExpense(form);
  if (!r.ok) { JR.ui.unlock('save'); /* 오류 표시 */ return; }
  // 성공: 화면 전환 후 unlock
  JR.ui.unlock('save');
}
```

동시에 **버튼 자체를 즉시 비활성화**합니다(화면설계 S-02 `저장` 규칙). 두 겹인 이유: 비활성화는 렌더 시점에 의존하고 키보드 반복 입력은 그 사이를 통과할 수 있습니다.

**데이터 계층은 중복을 판단하지 않습니다.** `addExpense` 는 같은 날짜·금액·카테고리·메모가 연속으로 들어와도 그대로 2건 저장합니다. 같은 가격의 커피를 두 잔 사는 것은 정상 사용이며, 데이터 계층이 이것을 막으면 사용자가 실제 지출을 기록할 수 없게 됩니다. **중복 방지 책임은 위 잠금 한 곳에만 둡니다.**

**삭제는 다릅니다.** `deleteExpense(id)` 를 두 번 부르면 두 번째는 `E-119`(대상 없음)로 실패합니다. 이미 없는 것을 지우려 한 것이므로 사용자에게는 알리지 않고(§7-9) 화면만 갱신합니다.

**사용자에게 보이는 결과**: 정상적인 더블탭에서는 아무 것도 보이지 않습니다(첫 클릭이 저장되고 두 번째는 조용히 삼켜짐 — 화면 전환이 이미 시작됐으므로). 키보드 반복 입력처럼 잠금 상태에서 명시적 조작이 반복되면 T 슬롯 `E-601` 이 뜹니다.

### 6-6. 새로고침 · 브라우저 뒤로 가기 — 입력 중이던 내용 (E-602 · E-603 · E-606)

**결정: 명시적으로 나가면 버리고, 사고로 사라지면 되살립니다.**

| 이탈 방식 | 초안 | 근거 |
|---|---|---|
| `저장` 성공 | 삭제 | 저장됐으므로 초안이 필요 없음 |
| `취소` → `나가기` 확정 | 삭제 | 사용자가 "사라집니다"에 동의함(화면설계 대화상자 문구) |
| 브라우저 뒤로 가기 → `나가기` 확정 | 삭제 | 위와 같음 |
| `이 기록 삭제` 확정 | 삭제 | 대상이 없어짐 |
| **새로고침(F5·당겨서 새로고침)** | **유지 → 복원** | 사용자가 내용을 버리겠다고 한 적이 없음 |
| **탭/브라우저 종료, 모바일에서 백그라운드 전환 후 앱이 종료됨** | **유지 → 복원** | 위와 같음 |

**저장 시점** (매 키 입력마다 쓰지 않습니다 — localStorage 쓰기 횟수를 줄이기 위해):

1. 날짜·금액·메모 입력란의 `change` 또는 `blur`
2. 카테고리 칩 선택
3. `visibilitychange` 에서 `document.visibilityState === 'hidden'` 일 때
4. `pagehide`

`beforeunload` 는 쓰지 않습니다. 모바일 브라우저에서 호출이 보장되지 않고, 확인창을 띄우는 부작용이 있습니다.

**초안 형태**는 §3-3 예시 그대로이며 `amount` 는 **사용자가 친 원문 문자열**입니다.

**복원 조건** (`loadDraft`)

| 조건 | 결과 |
|---|---|
| `savedAt` 이 없거나 정수가 아님 | 버림 · `E-603` |
| `Date.now() - savedAt > 86400000` (24시간) | 버림 · `E-603` |
| `mode === 'edit'` 인데 `targetId` 기록이 없음(그 사이 삭제됨) | 버림 · `E-603` |
| 그 외 | 복원 · `E-602` |

24시간을 고른 이유: 하루가 지난 뒤 앱을 열었을 때 옛날 입력이 폼에 채워져 있으면 사용자는 그것이 저장된 기록인지 초안인지 구분하지 못하고, 그대로 저장해 **잘못된 날짜의 기록**을 만듭니다. 하루 안이면 "아까 쓰다 만 것"이라는 맥락이 살아 있습니다.

**초안 저장 실패**(용량 부족 또는 메모리 모드에서의 재시작): `E-606` 을 T 슬롯에 **세션당 1회만** 표시합니다. 매 blur 마다 토스트가 뜨면 입력이 불가능해집니다.

**초안 복원이 화면설계와 충돌하지 않는 이유**: 화면설계의 `지금 나가면 입력한 내용이 사라집니다` 는 **명시적 이탈** 경로의 문구이고, 위 표에서 그 경로는 전부 "삭제"입니다. 새로고침은 그 대화상자를 거치지 않는 경로이므로 모순되지 않습니다.

**선택된 월은 초안과 무관하게 유지됩니다.** `settings.selectedMonth` 가 저장돼 있으므로 새로고침 후에도 같은 달을 봅니다(화면설계 §0-1 이 전제한 동작이며 §2-4 필드로 충족됩니다).

### 6-7. `file://` 에서 파일 다운로드가 막히는 경우 (E-401)

**확인 필요 — 사유: 저는 이 환경에서 브라우저를 실행해 볼 수 없습니다.** `file://` 문서에서 `<a download>` · `Blob` URL · `data:` URL 이 각각 동작하는지는 브라우저와 버전에 따라 다르며, 제가 단정하면 ④ 개발본부가 잘못된 전제로 구현하게 됩니다. 확인필요-5·7·8 로 남깁니다. **아래 폴백 사다리는 어느 것이 되든 사용자가 백업을 손에 넣도록 설계된 것이며, 세 단계가 모두 막혀도 F-08 은 실패하지 않습니다.**

| 순서 | 방법 | 사전 감지 | 실패 시 |
|---|---|---|---|
| 1 | `Blob` + `URL.createObjectURL` + `<a download>` 클릭 | `typeof Blob === 'function' && window.URL && typeof URL.createObjectURL === 'function' && ('download' in document.createElement('a'))` | 예외 발생 시 2번으로 |
| 2 | `data:application/json;charset=utf-8,` + `encodeURIComponent(json)` + `<a download>` 클릭 | `('download' in a)` | 예외 발생 시 3번으로 |
| 3 | **텍스트 대체 경로** — 화면설계 S-04 의 "내보내기 대체 영역"에 JSON 전문을 넣고 `E-401` 표시 | — | 없음(항상 성공) |

```js
JR.io.download = function (json, filename) {
  var a, url;
  try {
    if (typeof Blob === 'function' && window.URL && URL.createObjectURL) {
      a = document.createElement('a');
      if ('download' in a) {
        url = URL.createObjectURL(new Blob([json], {type: 'application/json'}));
        a.href = url; a.download = filename;
        document.body.appendChild(a); a.click(); document.body.removeChild(a);
        setTimeout(function () { try { URL.revokeObjectURL(url); } catch (e) {} }, 0);
        return JR.err.ok({ method: 'anchor-blob' });
      }
    }
  } catch (e) { JR.err.log('E-401', e); }
  try {
    a = document.createElement('a');
    if ('download' in a) {
      a.href = 'data:application/json;charset=utf-8,' + encodeURIComponent(json);
      a.download = filename;
      document.body.appendChild(a); a.click(); document.body.removeChild(a);
      return JR.err.ok({ method: 'anchor-data' });
    }
  } catch (e2) { JR.err.log('E-401', e2); }
  return JR.err.fail('E-401', { text: json });          // 3번 경로: 호출부가 text 를 화면에 붙임
};
```

**감지되지 않는 실패가 하나 있습니다.** 1·2번에서 `a.click()` 이 예외 없이 끝나도, 브라우저가 다운로드를 조용히 차단했는지는 **자바스크립트가 알 수 없습니다.** 그러면 사용자는 성공 토스트를 보지만 파일은 없습니다.

**대응 결정 — 데이터 계약만 확정합니다.** `JR.io.download` 는 **성공했을 때도 `data.text` 에 JSON 전문을 함께 반환**합니다. 이렇게 하면 UI 는 다운로드가 성공했다고 보고받은 뒤에도 대체 영역을 만들 재료를 이미 손에 쥐고 있습니다. 그 재료로 "성공했어도 대체 영역을 접힌 상태로 함께 노출할지"는 **화면 구성 결정이므로 `ux-designer` 소관**이며 제가 정하지 않습니다. §8 Q-012 로 남깁니다. 현재 화면설계는 "파일 저장이 막힌 경우에만" 대체 영역을 노출하도록 돼 있어, 조용한 차단 상황에서는 사용자가 백업을 얻지 못한 채 성공 토스트만 보게 됩니다.

`MAX_IMPORT_CHARS`(4,000,000)를 넘는 JSON 은 2번(`data:` URL)에서 실패할 가능성이 높습니다(URL 길이 상한). 이 경우 3번으로 내려가며, 3번 텍스트 영역은 길이 제한이 없습니다.

### 6-8. 브라우저가 필요한 API 를 지원하지 않음 (E-001 · E-002)

#### 6-8-1. 감지 표 (부팅 6단계에서 1회 실행)

| 등급 | API | 감지식 | 없으면 |
|---|---|---|---|
| 필수 | `JSON.parse`/`stringify` | `typeof JSON === 'object' && typeof JSON.parse === 'function'` | `E-001` |
| 필수 | `addEventListener` | `typeof window.addEventListener === 'function'` | `E-001` |
| 필수 | `document.querySelector` | `typeof document.querySelector === 'function'` | `E-001` |
| 필수 | `Object.keys` | `typeof Object.keys === 'function'` | `E-001` |
| 필수 | `Array.prototype.forEach`·`indexOf`·`filter`·`map` | 각각 `typeof [].forEach === 'function'` | `E-001` |
| 필수 | `String.prototype.trim` | `typeof ''.trim === 'function'` | `E-001` |
| 필수 | `Date.now` | `typeof Date.now === 'function'` | `E-001` |
| 준필수 | `localStorage` | §6-1 `probeStorage()` | `E-201`(메모리 모드로 계속) |
| 선택 | `Blob` · `URL.createObjectURL` · `a.download` | §6-7 표 | `E-002`(내보내기는 텍스트 경로로 계속) |
| 선택 | `FileReader` · `input[type=file]` | `typeof FileReader === 'function'` / `(function(){var i=document.createElement('input'); i.type='file'; return i.type==='file';})()` | `E-002`(가져오기 불가) |
| 선택 | `Array.from` | `typeof Array.from === 'function'` | 알리지 않음. §4-6 폴백 루프 사용 |
| 선택 | `document.visibilityState` | `typeof document.visibilityState === 'string'` | 알리지 않음. `pagehide` 만 사용 |
| 선택 | `Intl.Segmenter` | 사용하지 않음(§4-6) | — |

**필수 항목이 하나라도 없으면 앱 전체를 띄우지 않습니다.** `E-001` 문구는 **자바스크립트로 렌더하지 않습니다** — 자바스크립트가 부분적으로 죽은 환경에서 자바스크립트로 오류를 그리는 것은 신뢰할 수 없습니다.

```html
<!-- index.html 본문 최상단. 부팅이 필수 검사를 통과하면 boot.js 가 이 요소를 DOM 에서 제거합니다 -->
<div id="jr-unsupported">이 브라우저에서는 앱을 사용할 수 없습니다. 크롬·엣지·사파리·파이어폭스의 최신 버전에서 열어 주세요.</div>
<noscript>자바스크립트가 꺼져 있어 앱을 사용할 수 없습니다. 브라우저 설정에서 자바스크립트를 켜고 새로고침해 주세요.</noscript>
```

`#jr-unsupported` 의 배치·스타일은 ③ 디자인본부 영역입니다. 데이터 계약은 **요소 id 와 "부팅 성공 시 제거된다"는 규칙**뿐입니다.

#### 6-8-2. 선택 API 부재 (E-002)

기능을 **숨기지 않고 비활성 상태로 둡니다.** 버튼이 사라지면 사용자는 자기 기억을 의심합니다. `가져오기` 버튼이 비활성이면 `E-002` 배너가 그 이유를 설명합니다.

| 없는 것 | 비활성화되는 것 | 계속 되는 것 |
|---|---|---|
| `FileReader` 또는 `input[type=file]` | S-04 `가져오기` | 내보내기·기록·통계 전부 |
| `Blob`·`download` 전부 | 없음(§6-7 3번 텍스트 경로로 대체) | 전부 |

#### 6-8-3. 백그라운드 전환 (E-604 · E-605)

모바일에서 앱을 백그라운드로 보내면 브라우저가 탭을 통째로 정리할 수 있습니다. 그 시점에 메모리에만 있던 것은 사라집니다.

**전환 시(`visibilitychange` → `hidden`, 그리고 `pagehide`)**

1. S-02 에 있으면 초안 저장(§6-6).
2. 진행 중인 `applyImport` 트랜잭션이 있으면 아무 것도 하지 않습니다(동기 실행이라 이 시점에 걸릴 수 없습니다).
3. 마지막으로 읽은 `meta.lastWriteAt` 값을 메모리 변수 `lastSeenWriteAt` 에 보관합니다.

**복귀 시(`visibilitychange` → `visible`)**

```js
var r = JR.store.getJSON('jr.v1.meta');
if (r.ok && r.data.value && r.data.value.lastWriteAt !== lastSeenWriteAt) {
  // 다른 탭/창이 같은 데이터를 바꿨다
  JR.model.init();            // 다시 읽어 메모리 상태를 맞춘다
  JR.stats.invalidate();
  JR.ui.toast('E-605');       // 화면을 다시 그렸다는 사실을 알린다
}
```

| 상황 | 코드 | 결과 |
|---|---|---|
| 백그라운드 전환 직전 초안 저장이 실패 | `E-604` | 복귀 시 B 슬롯. 초안이 없을 수 있음을 알림 |
| 다른 탭이 데이터를 바꿈 | `E-605` | 복귀 시 데이터 재로드 + T 슬롯 |
| 아무 변화 없음 | 없음 | 화면 그대로. **아무 것도 표시하지 않습니다** |

**확인 필요 — `file://` 에서 여러 탭이 같은 localStorage origin 을 공유하는지 브라우저마다 다릅니다**(Chromium 은 `--allow-file-access-from-files` 여부에 따라, Firefox 는 정책이 다릅니다). 공유되지 않으면 `E-605` 는 영원히 발생하지 않으며, 그래도 위 코드는 무해합니다. 확인필요-2·3 으로 남깁니다.

## 7. E-코드 전체 표

### 7-0. 표를 읽는 법

| 열 | 의미 |
|---|---|
| 코드 | `js/err.js` 의 `MESSAGES` 키. **이 표가 단일 출처**입니다 |
| 슬롯 | `T` 토스트 · `I` 인라인 · `B` 배너 (분배안 §3-5). `I` 는 대상 필드를 괄호로 함께 적습니다 |
| 발생 조건 | 코드가 이 조건을 그대로 검사할 수 있게 씁니다. "이상한 값이면" 같은 표현을 쓰지 않았습니다 |
| 사용자에게 보이는 문구 | **화면에 그대로 나가는 완성된 한국어 문장**입니다. `{...}` 는 `JR.err.format` 이 치환하는 자리표시자이며, 채우는 값을 옆에 적었습니다 |
| 복구 경로 | 이 문구를 본 사용자가 다음에 무엇을 할 수 있는가 |

**문구 원칙 4가지** — 새 코드를 추가할 때도 지키십시오.

1. **무엇이 어떻게 됐는지 먼저, 무엇을 하면 되는지 다음.** 원인 설명은 필요한 만큼만.
2. **데이터가 남았는지 사라졌는지를 반드시 밝힙니다.** 이 앱에서 사용자가 가장 두려워하는 것은 기록 소실이고, 침묵은 최악을 상상하게 만듭니다.
3. 기술 용어(localStorage · JSON · 파싱 · 스키마 · 쿼터)를 문구에 쓰지 않습니다.
4. 사용자를 탓하지 않습니다("잘못 입력했습니다" ✕ / "숫자만 입력할 수 있습니다" ○).

`E-502` 와 `E-599` 는 **정상 동작에서는 절대 발생하지 않아야 하는 코드**입니다. 발생하면 `JR.err.log` 가 콘솔에 원인을 남기므로 ④ 개발본부가 테스트 중에 잡아야 합니다.

### 7-7. 화면설계 슬롯과의 대조

`ux-designer` 가 지정한 슬롯 위치와 위 표를 한 줄씩 맞춰 봤습니다. **불일치 2건을 발견해 아래에 처리 규칙을 적었습니다.**

| 화면설계가 지정한 것 | 대응 E-코드 | 일치 여부 |
|---|---|---|
| S-02 날짜 "범위를 벗어난 값 → 저장 시 I 슬롯" | E-107~E-111 (I) | 일치 |
| S-02 금액 "범위를 벗어난 숫자 → 저장 시 I 슬롯" | E-101~E-106 (I) | 일치 |
| S-02 "카테고리 미선택 시 저장 버튼 비활성" | E-112 (I) — 버튼이 비활성이므로 평소엔 뜨지 않고, 키보드 조작 등으로 통과했을 때의 두 번째 방어선 | 일치 |
| S-04 카테고리 이름 "1~12자·공백·중복 → I 슬롯" | E-114·E-115·E-116 (I) | 일치 |
| S-04 "가져오기 형식 오류 → T 슬롯, 대화상자 없이 종료" | E-403~E-408 (T) | 일치 |
| S-04 "내보내기 대체 영역" | E-401 (T) + 화면설계 안내문 | 일치 |
| S-01·S-03·S-04 최상단 B 슬롯 | E-2xx·E-3xx·E-410·E-411·E-002 (B) | 일치 |
| **S-02 에는 B 슬롯 행이 없음** | E-202·E-205 등이 저장 실패로 S-02 에서 발생 | **불일치 — 아래 규칙** |
| **메모 필드 "별도 오류 없음"** | E-120·E-121·E-123 | **불일치 — 아래 규칙** |

**불일치 1 — S-02 에 배너 자리가 없습니다.** 저장 실패(`E-202`·`E-205`)는 S-02 에서 발생하는데 그 화면에는 B 슬롯이 정의돼 있지 않습니다.

> **처리 규칙(확정)**: S-02 에 머무는 동안 `slot === 'B'` 인 코드가 발생하면 **T 슬롯으로 대체 표시**합니다. 동시에 `notices` 에 남으므로, 사용자가 S-01·S-03·S-04 로 이동하는 순간 배너로 다시 나타납니다. 정보가 사라지지 않으며, 화면설계를 고치지 않고도 동작합니다. §8 Q-010 으로 통합 검토를 요청합니다.

**불일치 2 — 메모 필드에 인라인 오류 자리가 없습니다.** 화면설계는 메모 오른쪽 아래를 글자 수 표시(`0/100`)로 쓰고 "별도 오류 없음"으로 적었습니다.

> **처리 규칙(확정)**: 메모 관련 코드 `E-120`·`E-121`·`E-122`·`E-123` 은 전부 **T 슬롯**입니다. 슬롯 위치는 `ux-designer` 소관이므로 제가 새 인라인 자리를 만들지 않습니다. §8 Q-008 로 통합 검토를 요청합니다.

**화면설계의 확인 요청 3건에 대한 답**

| 화면설계 §가정 | 답 |
|---|---|
| 1. 선택된 월이 재실행 후에도 유지되는가 | **예.** `Settings.selectedMonth`(§2-4)에 `YYYY-MM` 문자열로 저장되며 `jr.v1.settings` 키에 들어갑니다. 조회는 `JR.model.getSettings()`, 변경은 `JR.model.setSelectedMonth(yyyymm)` 입니다 |
| 2. 마지막 카테고리 삭제 금지가 데이터 규칙과 충돌하는가 | **충돌하지 않습니다.** 데이터 계층도 같은 규칙을 강제합니다 — `deleteCategory` 는 카테고리가 1개일 때 `E-118` 로 거부합니다(§2-2). 기본 카테고리(`isDefault:true`)도 삭제 가능하며, 막는 유일한 조건은 "마지막 1개"입니다 |
| 3. 내보내기 대체 경로의 실제 동작 | §6-7 3단 폴백입니다. UI 가 받는 것은 `{ok:false, code:'E-401', data:{text}}` 이며 `data.text` 가 대체 영역 텍스트 영역에 넣을 JSON 전문입니다. 성공 시에도 `data.text` 가 함께 옵니다(§6-7) |

**화면설계가 확정한 라벨 `미분류(삭제된 카테고리)` 를 데이터 계층이 그대로 씁니다.** `JR.model.getCategoryName()` 과 `StatItem.categoryName` 이 이 문자열을 반환합니다(§5-4-4·§5-5). §2-7 주1 의 Q-007 은 이것으로 해소를 제안하며, 최종 판정은 `product-planner` 통합 시입니다.

### 7-8. B 슬롯 배너 표시·닫기 정책 (`dismissedNotices` 의 용도)

배너를 세 종류로 나눕니다. **화면설계 §0-2 의 "문제가 남아있는 한 다음 화면 진입 시 다시 노출"** 규칙을 그대로 따르되, "문제가 남아있는지"를 코드별로 판정합니다.

| 종류 | 해당 코드 | 닫기 | 닫은 뒤 |
|---|---|---|---|
| **상태형** — 원인이 지금도 계속됨 | E-201 · E-202 · E-205 · E-002 | 가능 | 화면을 옮기면 **다시 나타납니다.** `dismissedNotices` 에 기록하지 않습니다 |
| **사건형** — 이미 끝난 일을 알리는 것 | E-203 · E-301 · E-302 · E-303 · E-304 · E-305 · E-410 · E-604 | 가능 | 이 세션 동안 다시 나타나지 않습니다. `dismissedNotices` 에 기록합니다 |
| **차단형** — 닫으면 사용자가 위험해짐 | E-307 · E-411 | **불가** | 닫기 버튼 자체를 만들지 않습니다 |

**`noticeKey` 형식**: `'<코드>:<발생시각epochMs>'` — §3-3 예시의 `"E-303:1786512000000"` 이 이것입니다. 발생 시각은 그 사건을 감지한 순간의 `Date.now()` 이며 세션 동안 고정됩니다. 다음 실행에서 같은 사건이 또 감지되면 **새 키가 생겨 배너가 다시 나타납니다.** 손상이 반복되고 있다는 사실을 사용자에게 계속 알리기 위함입니다.

`dismissedNotices` 는 최대 20개이고 초과 시 앞에서부터 버립니다(§2-4). 20개를 넘길 만큼 사건이 쌓였다면 가장 오래된 것은 이미 의미가 없습니다.

**표시 순서**: `notices` 배열에 여러 코드가 있으면 배너를 여러 개 쌓지 않고 **가장 심각한 것 하나만** 띄웁니다. 우선순위는 `E-307` > `E-411` > `E-202` > `E-205` > `E-201` > `E-303` > `E-305` > `E-304` > `E-410` > `E-302` > `E-301` > `E-604` > `E-203` > `E-002` 입니다. 나머지 코드는 배너가 닫힌 뒤 순서대로 표시합니다.

### 7-9. 알리지 않고 처리하는 것 (폴백표)

**모든 예외를 사용자에게 말하면 아무 말도 안 한 것과 같아집니다.** 아래는 감지하고 처리하되 화면에 아무 것도 띄우지 않는 항목입니다. 각 항목에는 알리지 않는 이유가 있습니다.

| 상황 | 처리 | 알리지 않는 이유 |
|---|---|---|
| `memo` 앞뒤 공백 제거(§2-1 1) | `trim` | 사용자가 의도한 값과 결과가 같습니다 |
| `memo` 제어문자 제거(§2-1 3) | 제거 후 저장 | 사용자가 입력한 적 없는 문자입니다(붙여넣기 부산물). 설명할 대상이 없습니다 |
| `settings.selectedMonth` 가 범위 밖 → 경계값으로 보정(§6-3-3) | 보정 | 화면에는 보정된 달이 보이므로 결과가 즉시 확인됩니다 |
| 정상 더블탭의 두 번째 클릭(§6-5) | 삼킴 | 첫 클릭이 성공했고 화면이 이미 바뀌었습니다. 토스트는 성공을 실패로 오해하게 만듭니다 |
| 삭제 확정 버튼이 두 번 눌려 두 번째가 `E-119` 를 받음 | 삼킴 | 사용자가 원한 결과(삭제됨)가 이미 이뤄졌습니다. 단 **목록에서 사라진 기록을 다시 열려고 할 때는 `E-119` 를 표시합니다** — 이때는 사용자가 결과를 모르기 때문입니다 |
| 파일 선택 대화상자를 사용자가 취소(V-1) | 아무 것도 안 함 | 사용자가 스스로 취소한 것입니다 |
| `URL.revokeObjectURL` 실패(§6-7) | `try/catch` 로 삼킴 | 메모리 정리 실패일 뿐 사용자 데이터와 무관합니다 |
| `Array.from` 없음 → 수동 루프(§4-6) | 폴백 사용 | 결과가 동일합니다 |
| `document.visibilityState` 없음 | `pagehide` 만 사용 | 초안 저장 시점이 하나 줄 뿐 동작은 같습니다 |
| 캐시 무효화·`monthIndex` 재구축(§4-4) | 자동 | 내부 최적화입니다 |
| dangling `categoryId` 를 `미분류(삭제된 카테고리)` 로 표시(§2-7) | 표시 | 오류가 아니라 설계된 동작이며, 삭제 시점의 확인 대화상자에서 이미 알렸습니다 |
| `JR.err.log` 의 모든 콘솔 출력 | `console.warn` | 개발자용입니다 |

## 9. 확인 필요 — ④ 개발본부가 실측할 항목

**아래는 제가 검증할 수 없는 것들입니다.** 저는 이 환경에서 브라우저를 실행할 수 없으므로, `file://` 에서의 실제 동작을 단정하지 않고 남깁니다. 각 항목에 **실측 방법**과 **결과에 따른 분기**를 함께 적었으므로, 실측 후 이 문서를 고칠 필요 없이 그대로 구현할 수 있습니다.
