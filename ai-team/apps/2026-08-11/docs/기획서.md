## 1. 제품 정의

| 항목 | 값 |
|---|---|
| 앱 이름(가칭) | **정레** — 확정 아님. 이름 확정은 ③ 디자인본부(브랜드) 영역 |
| 한 줄 정의 | 로그인 없이 기기 안에만 저장되는 수기 입력형 지출 기록 · 카테고리별 통계 앱 |
| 실행 방식 | 브라우저에서 `index.html` 을 `file://` 로 직접 열기. 서버 없음, 설치 없음, 네트워크 요청 0건 |

| 날짜 | 로컬 시간 기준 `YYYY-MM-DD` 문자열 저장. `Date` 객체를 직렬화하지 않음 |

확정 요약:

| 항목 | 확정값 |

| 목록 정렬 | `date` ↓ → `createdAt` ↓ → `id` ↓ (0을 반환하지 않는 전순서 → 새로고침해도 순서 불변) |

| 카테고리 삭제 시 기록 | **기록을 지우지 않고 `categoryId` 를 남깁니다**(dangling 허용). 통계에서는 `__deleted__` 하나로 합산, 항상 마지막 항목 |
| 용량 상한 상수 | `JR.store.LIMIT_CHARS = 2500000` — **보수적 추정치. ④ 실측 항목 #6** |
| 가져오기 파일 상한 | `JR.io.MAX_IMPORT_CHARS = Math.floor(JR.store.LIMIT_CHARS / 4)` = **625,000** (2.5M 기준). 독립 상수 `4000000` 폐기 — **INT-27** |
| 가져오기 피크 사용량 | `usage().usedChars`(롤백 사본 포함) + 새 데이터 2벌. 산정표 행은 **INT-27** 에 있습니다 |

## 5. API 정의 (② 게이트 항목 4/5)

**정본: `docs/기획-구조설계.md` §5.** 모듈 6개(`JR.err`·`JR.store`·`JR.model`·`JR.stats`·`JR.io`·`JR.ui`)의 공개 함수 시그니처·인자·반환 형태가 전부 확정되어 있습니다.

핵심 계약:

- 반환 규약: 성공 `{ok:true, data:{...}}` / 실패 `{ok:false, code:'E-xxx', data:{...}}`
- **예외를 던지지 않습니다.** 모든 공개 함수는 내부 `try/catch`, 예상 못 한 예외는 `E-501`
- `{ok}` 로 감싸지 않는 함수는 **정확히 12개** — 순수 계산 9개(`today`·`minDate`·`maxDate`·`countChars`·`normName`·`shiftMonth`·`monthRange`·`allocatePercents`·`formatAmount`) + 상태 조회 3개(`store.mode`·`model.isReady`·`model.isNoticeDismissed`). **이 목록에 함수를 추가하지 마십시오**
- 스크립트 로드 순서 고정: `err → store → model → stats → io → ui → boot`
- 역방향 호출 허용은 1건뿐: `JR.model` 쓰기 성공 직후 `JR.stats.invalidate()` (존재 확인 후 호출)
- `JR.ui` 고정 함수: `toast` · `inline` · `banner` · `dismissBanner` + `lock` · `unlock` + **`show`(INT-15 로 필수화)**

> **§5 를 읽기 전에 §7-9 를 먼저 보십시오.** 구조설계 §5 의 아래 4곳은 §7-9 가 덮어씁니다 — **INT-24**(§4-4 무효화 트리거 목록의 `applyImport`→`replaceAll` · §5-1 `JR.io` 행의 `JR.stats` 금지 명시 · §6-4-2 5단계 `invalidate()` 삭제) · **INT-25**(`monthIndex` 소유 = `JR.model`) · **INT-27**(`MAX_IMPORT_CHARS` 파생 상수화 · `V-3-1` · `E-413`) · **INT-32·INT-33**(구조설계 §7 표의 `E-413` **슬롯 열** 및 `E-403`·`E-121`·`E-306` **문구 열** · §7-8 배너 사건형 목록과 우선순위) · **INT-30**(`E-307` 읽기 함수 반환 · `isReady()` = `false` · `E-502` 방어 범위). **`{ok}` 로 감싸지 않는 함수 12개 목록과 공개 함수 시그니처는 한 건도 바뀌지 않았습니다.**

## 7. 통합 확정 (INT) — **하위 문서보다 우선합니다**

두 문서를 맞대어 본 결과입니다. **구멍 3건(두 문서가 서로 어긋남) · 구멍 2건(문서 내부 자기모순) · 미정의 8건(어느 문서에도 답이 없음)** 을 찾아 전부 닫았습니다. 각 항목은 ④ 가 추가 질문 없이 구현할 수 있는 형태로 씁니다.

### 7-1. 어긋남을 닫은 것

#### INT-01 · S-02 에도 B 슬롯이 있습니다 (구조설계 Q-010 **기각**)

- **상황**: 구조설계 §7-7 은 "S-02 요소표에 배너 행이 없다"를 불일치로 보고, S-02 에서는 B 코드를 T 로 대체 표시하는 잠정 규칙을 세웠습니다.
- **재검토 결과**: 화면설계 §0-2 공통 규칙 표는 배너의 노출 화면을 **"4개 화면 공통"** 으로 이미 명시했습니다. S-02 요소표에 행이 없는 것은 공통 규칙에 이미 있어 반복하지 않은 것이며, 슬롯 자체는 존재합니다.
- **확정**: **S-02 에도 B 슬롯 배너를 그대로 표시합니다.** 위치는 화면 최상단(상단 제목·`취소` 버튼보다 위), 스크롤 무관 고정. 구조설계의 "T 로 대체" 규칙은 **채택하지 않습니다.**
- **사유**: E-202 문구는 3문장(`저장 공간이 가득 차 … 이전 기록은 그대로 있습니다. … 내보내기로 백업한 뒤 …`)이라 3초 후 사라지는 토스트로는 읽을 수 없습니다. 데이터 소실 가능성 고지는 사용자가 닫을 때까지 남아야 합니다(`team-rules.md:38` 의견 충돌 해결 ④ 보안·안정성 우선).

#### INT-07 · 통계에서 `미분류(삭제된 카테고리)` 는 **항상 마지막**

- **상황**: 화면설계 S-03 은 "미분류 항목도 동일 규칙(금액 내림차순)으로 포함", 구조설계 §4-3-1 은 "`__deleted__` 는 금액이 크더라도 항상 마지막".
- **확정**: **구조설계를 채택합니다.** `JR.stats.byCategory()` 가 반환한 `items` 배열 순서를 UI 가 **그대로** 그립니다. UI 는 재정렬하지 않습니다.
- **사유**: 정렬 책임이 두 곳에 있으면 어긋납니다. 사용자가 정상 카테고리를 먼저 보는 것이 맞습니다.

#### INT-06 · dangling 카테고리 라벨은 `미분류(삭제된 카테고리)` 하나

- **상황**: 구조설계 §2-7 항목1 은 `삭제된 카테고리`, 같은 문서 §5-4-4·§5-5·§7-7 은 `미분류(삭제된 카테고리)` — **구조설계 내부에서 두 값이 병존**합니다.
- **확정**: **`미분류(삭제된 카테고리)`** 단일. 구조설계 §2-7 항목1 의 값은 폐기합니다. `JR.model.getCategoryName()` 과 `StatItem.categoryName` 이 이 문자열을 반환하며, 이 라벨은 표시 전용이고 카테고리 선택 목록에 나타나지 않습니다.
- Q-007 · Q-009 **종결**.

### 7-2. 자기모순을 닫은 것

#### INT-02 · S-02 `저장` 버튼의 비활성 조건을 **축소**합니다

- **상황(화면설계 내부 모순)**: 금액 필드 행은 "범위를 벗어난 숫자는 입력은 되지만 **저장 시 I 슬롯 오류**"라고 쓰고, 같은 화면의 `저장` 버튼 비활성 조건에는 "금액 … 범위 밖"이 들어 있습니다. 버튼이 비활성이면 저장 시도 자체가 불가능하므로 두 서술은 동시에 성립할 수 없습니다. 이대로 두면 **E-103·E-104·E-105·E-106·E-107·E-109·E-110·E-111 여덟 개 코드가 영원히 도달하지 않는 죽은 코드**가 됩니다.
- **확정 — `저장` 버튼 비활성 조건은 아래 4가지뿐입니다.**

| # | 비활성 조건 |
|---|---|
| 1 | 날짜 입력값이 빈 문자열 |
| 2 | 금액 입력값이 (쉼표·공백 제거 후) 빈 문자열 |
| 3 | 카테고리 미선택 **또는** 등록된 카테고리가 0개 |
| 4 | `JR.ui.lock('save')` 로 잠긴 동안 (저장 처리 중) |

- 형식 위반·범위 위반(0원, 10억, 소수점, 2026-02-30, 1999년, 오늘+2년)은 **버튼이 활성**이며, 누르면 해당 I 슬롯 오류가 뜹니다.
- **사유**: 비활성 버튼은 이유를 말해주지 못합니다. 사용자가 "왜 저장이 안 되지"에서 멈춥니다. 값을 **비운 것**(아직 입력 안 함)과 값이 **틀린 것**(고칠 지점이 있음)은 다르게 다뤄야 합니다.

#### INT-03 · S-04 카테고리 `추가` · `확인` 버튼의 비활성 조건도 같은 원칙으로 축소

| 버튼 | 비활성 조건 (이것뿐) |
|---|---|
| `추가` | 입력값이 빈 문자열이거나 공백만 · 카테고리가 이미 20개 · `JR.ui.lock('category-add')` 잠금 중 |
| 편집 상태의 `확인` | 입력값이 빈 문자열이거나 공백만 · 잠금 중 |

- 12자 초과(E-115)·이름 중복(E-116)은 **버튼 활성** → 누르면 I 슬롯 오류. 자기 자신과 같은 이름으로 바꾸는 것은 중복이 아니며 성공 처리합니다(토스트 `카테고리 이름을 바꿨습니다`).
- 카테고리 20개 도달 시에는 입력란·`추가` 버튼을 비활성하고 안내문 `카테고리는 최대 20개까지 만들 수 있습니다.` 를 노출합니다(화면설계 그대로). 이때 E-117 은 두 번째 방어선입니다.

### 7-3. 문구 중복·자리표시자를 닫은 것

#### INT-04 · 카테고리 미선택 안내는 **E-112 문구 하나만** 씁니다

- **상황**: 화면설계 S-02 가 카테고리 영역에 안내 문구 `카테고리를 선택해 주세요.` 를 확정했는데, 구조설계 E-112(I, categoryId)의 문구가 **글자까지 동일**합니다. 같은 자리에 같은 문장이 두 출처에서 나옵니다(분배안 §5 경계 위반은 아니나 이중 정의).
- **확정**:
  - 문구의 단일 출처는 **`JR.err.MESSAGES['E-112']`** 입니다. 화면설계의 별도 안내 문구는 폐기합니다.
  - 표시 시점: **카테고리가 선택되지 않은 동안 상시** 표시(추가 모드 진입 직후 포함). 저장 시도 시 새로 띄우지 않습니다(이미 떠 있음).
  - 선택되는 순간 사라집니다(I 슬롯 규칙).
  - 이 문구를 "오류로 강조할지, 중립 안내로 보일지"는 **③ 디자인본부가 정합니다.** 문구와 표시 시점은 여기서 확정됐습니다.

#### INT-05 · 날짜 필드 안내 문구의 `(오늘로부터 1년 뒤)` 를 실제 날짜로 치환

- **상황**: 화면설계가 확정한 안내문이 `2000-01-01 ~ (오늘로부터 1년 뒤) 사이 날짜만 입력할 수 있습니다.` 입니다. 괄호 안을 그대로 화면에 출력할지 실제 날짜를 넣을지가 정해져 있지 않습니다.
- **확정 문구**: `2000-01-01 ~ {max} 사이 날짜만 입력할 수 있습니다.`
  - `{max}` = `JR.model.maxDate()` 의 반환값을 그대로 삽입. 예: 2026-08-15 에 열면 `2000-01-01 ~ 2027-08-15 사이 날짜만 입력할 수 있습니다.`
  - 괄호 표현 `(오늘로부터 1년 뒤)` 를 화면에 출력하지 않습니다.

### 7-4. 어느 문서에도 없던 것을 확정한 것

#### INT-10 · 내보내기 대체 영역은 **성공했을 때도 노출**합니다 (구조설계 Q-012 확정)

- **상황**: `a.click()` 이 예외 없이 끝나도 브라우저가 다운로드를 조용히 차단했는지 자바스크립트가 알 수 없습니다(구조설계 §6-7 이 스스로 밝힌 사각지대). 화면설계는 "파일 저장이 막힌 경우에만" 대체 영역을 노출하도록 했으므로, 조용히 차단되면 **사용자는 성공 토스트만 보고 백업을 얻지 못합니다.**
- **확정**: `내보내기` 버튼을 누르면 `download()` 의 성공·실패와 **무관하게** 대체 영역을 노출합니다. 안내문만 2종으로 갈립니다.

| 상황 | 대체 영역 안내문 | 함께 뜨는 토스트 |
|---|---|---|
| 성공 (`method` = `anchor-blob` 또는 `anchor-data`) | **`파일을 저장했습니다. 저장된 파일이 보이지 않으면 아래 내용을 복사해 보관하세요.`** (② 파트장 신규 확정 문구) | `내보내기를 완료했습니다` |
| 실패 (`E-401`) | `파일 저장이 지원되지 않는 환경입니다. 아래 내용을 직접 복사해 보관하세요.` (화면설계 확정 문구 그대로) | `E-401` |

- 영역 구성은 화면설계 그대로: 안내문 + 읽기전용 텍스트 영역(JSON 전문) + `전체 선택` 버튼.
- 영역은 S-04 를 벗어나면 사라지고, 다시 `내보내기` 를 누르면 다시 나타납니다.
- 재료는 이미 확보되어 있습니다 — `JR.io.download()` 는 **성공 시에도 `data.text` 에 JSON 전문을 반환**합니다(구조설계 §6-7).
- **사유**: 잃는 것은 화면 한 칸이고, 얻는 것은 "백업했다고 믿었는데 파일이 없는" 사고의 차단입니다.

#### INT-12 · 초안 복원과 S-02 진입 규칙 (두 문서 모두 미정의)

구조설계 §6-6 은 초안을 언제 저장·폐기할지는 정했지만, **화면 어디에서 복원되는지**는 정해지지 않았습니다. 확정합니다.

1. **부팅 후 첫 화면은 항상 S-01 입니다.** 초안이 있어도 S-02 를 자동으로 열지 않습니다.
2. 초안 복원은 **S-02 진입 시점**에 `JR.model.loadDraft()` 로 1회 시도합니다.
3. 폼에 채우는 조건 — **아래를 모두 만족할 때만**:
   - `draft.mode` 가 이번 진입 모드(`'add'` / `'edit'`)와 같음
   - `mode === 'edit'` 이면 `draft.targetId` 가 이번에 여는 기록의 `id` 와 같음
   - `loadDraft()` 가 `data.code === null` 로 반환 (만료·대상 소실이 아님)
4. 조건을 만족하지 않으면 초안을 **조용히 버리고**(`clearDraft()`) 기본값으로 폼을 엽니다. 사용자에게 알리지 않습니다 — 그 초안은 지금 열려는 화면의 것이 아닙니다.
5. 복원되면 T 슬롯 `E-602`. 만료로 폐기되면 T 슬롯 `E-603` (S-02 진입 직후).
6. **복원된 상태는 "변경 있음"으로 간주합니다.** 이 상태에서 `취소` 또는 브라우저 뒤로 가기를 누르면 나가기 확인 대화상자가 뜹니다.

#### INT-13 · S-04 `가져오기` 버튼의 비활성 조건 추가

화면설계는 "처리 중"만 적었습니다. 여기에 추가합니다: **`FileReader` 또는 `input[type=file]` 미지원**(구조설계 §6-8-1 감지 결과). 이때 `E-002` 배너가 그 이유를 설명하고, 버튼은 **숨기지 않고 비활성**으로 둡니다(구조설계 §6-8-2 원칙). 버튼을 눌러 보려 한 경우의 두 번째 방어선은 `E-412` 입니다.

#### INT-15 · `JR.ui.show()` 는 권장이 아니라 **필수**입니다

구조설계 §5-8 은 슬롯 판정 헬퍼를 "두는 것을 권합니다"로 적었습니다. **권장을 확정으로 올립니다.** 모든 E-코드 표시는 `JR.ui.show(code, params, field)` 한 경로로만 나갑니다. `JR.ui.toast/inline/banner` 를 호출부에서 직접 부르지 않습니다(성공 문구 표시는 예외 — INT-16).

- 사유: 슬롯 판정이 호출부마다 흩어지면 E-코드 64개 × 호출 지점 수만큼 어긋날 자리가 생깁니다. ⑤ QA 가 "이 코드가 맞는 슬롯에 떴는가"를 한 곳에서 검증할 수 있어야 합니다.
- INT-01 로 S-02 에도 B 슬롯이 있으므로, 화면별 슬롯 대체 분기는 **필요 없습니다.** `show()` 는 화면을 알 필요가 없습니다.

#### INT-19 · 목록에서 이미 사라진 기록을 열려고 할 때

기록 행을 눌렀는데 `JR.model.getExpense(id)` 가 `E-119` 를 반환하면(다른 탭에서 삭제된 경우): **S-02 로 진입하지 않고** S-01 에 머물며 T 슬롯 `E-119` (`이미 삭제된 기록입니다. 목록을 새로 불러왔습니다.`) 표시 후 목록을 다시 그립니다. 구조설계 §7-9 가 "목록에서 사라진 기록을 다시 열려고 할 때는 알린다"고 한 경로가 이것입니다.

#### INT-20 · 금액 입력란의 구현 계약

화면설계는 "숫자가 아닌 문자는 입력되는 순간 걸러진다 + 천 단위 쉼표 자동 표시"를 정했습니다. 구현이 갈릴 수 있는 3가지를 확정합니다.

| 항목 | 확정 |
|---|---|
| 입력 요소 | `<input type="text" inputmode="numeric" autocomplete="off">`. **`type="number"` 를 쓰지 않습니다** — 쉼표를 표시할 수 없고 브라우저마다 소수점·지수 입력을 허용합니다 |
| 필터 시점 | `input` 이벤트에서 `value.replace(/[^0-9]/g, '')` → 9자리 초과분은 자르지 않고 그대로 둠(E-104 가 저장 시 막음) → 천 단위 쉼표 재삽입. 붙여넣기도 같은 경로를 탑니다 |
| 커서 위치 | 쉼표 재삽입 후 커서를 **문자열 끝**으로 보냅니다. 중간 편집 시 커서 오프셋을 재계산하지 않습니다 — 순수 JS 로 정확히 맞추려면 분기가 늘고, 금액은 대개 끝에서 이어 칩니다 |
| 데이터 계층 전달 | UI 는 **쉼표가 붙은 원문 문자열을 그대로** `JR.model` 에 넘깁니다. UI 에서 미리 파싱하지 않습니다(파싱 규칙이 두 곳에 생기면 어긋납니다 — 구조설계 §5-4-3) |

이 필터 때문에 `E-102`(숫자 아님)·`E-105`(소수점)·`E-106`(숫자 변환 불가)은 **정상 조작으로는 도달하지 않는 두 번째 방어선**입니다. 삭제하지 마십시오 — 붙여넣기·IME·자동완성 경로가 필터를 우회할 수 있습니다.

#### INT-21 · 날짜 입력란의 구현 계약

| 항목 | 확정 |
|---|---|
| 입력 요소 | `<input type="date" min="2000-01-01" max="{maxDate()}">` |
| 미지원 브라우저 | 브라우저가 `text` 로 폴백합니다. 이때 방어선은 `E-107`(형식) → `E-109`(실재하지 않는 날짜) → `E-110`/`E-111`(범위) 순서입니다 |
| 데이터 계약 | 어느 경우에도 `JR.model` 에 넘기는 값은 `YYYY-MM-DD` 문자열입니다 |
| `min`/`max` 속성 | 신뢰하지 않습니다. 검증은 항상 `JR.model.validateExpense` 가 합니다 |

**`setSelectedMonth` 는 무효화하지 않습니다 (② 확정 · 파생 결정 1건)**. 구조설계 §5-1 의 `notifyChange(kind)` 는 `kind` 를 가리지 않고 `invalidate()` 를 부르는데, `setSelectedMonth` 도 `notifyChange('settings')` 를 부르므로 **월을 이동할 때마다 캐시가 통째로 버려집니다.** `statsCache` 는 `yyyymm` 별 키이고 월 이동은 집계 **결과를 바꾸지 않으므로** 버릴 이유가 없습니다. 아래 한 줄로 확정합니다.

```js
function notifyChange(kind) {                       // kind: 'expense' | 'category' | 'settings' | 'bulk'
  if (kind !== 'settings' && JR.stats && typeof JR.stats.invalidate === 'function') JR.stats.invalidate();
  // monthIndex 재구축(INT-25)도 kind !== 'settings' 일 때만 수행합니다
  ...                                               // subscribers 통지는 kind 와 무관하게 항상 수행
}
```

`dismissNotice` 도 `'settings'` 로 통지합니다(같은 이유로 무효화 대상 아님).

**이 판정으로 막는 사고**: 두 개발자가 각자 문서를 정직하게 따랐을 때 아무도 `invalidate()` 를 부르지 않아 「가져오기 성공 → 통계 탭에 옛 막대」가 나오는 것. 무효화 책임이 `JR.model` 한 곳에만 있으므로 `io.js` 담당자는 이 문제를 알 필요조차 없습니다.

#### INT-27 · 가져오기 트랜잭션의 저장소 피크를 닫습니다 (Q-022 **인정** · 상수 변경 + `E-413` 신설)

**1) `MAX_IMPORT_CHARS` 를 `LIMIT_CHARS` 에서 파생시킵니다.**

```js
JR.io.MAX_IMPORT_CHARS = Math.floor(JR.store.LIMIT_CHARS / 4);   // 2,500,000 → 625,000
```

- 독립 상수 `4000000` 은 **폐기**합니다. 저장소 상한(2.5M)보다 큰 값이라 **물리적으로 저장할 수 없는 파일이 V-3 을 통과**했습니다.
- 나누는 수 **4 의 근거**: §6-4-2 3단계 시점의 피크는 `롤백 사본(= 트랜잭션 직전 사용량 U)` + `새 데이터 + 새 .bak(≈ 2X)` 입니다. 가져올 파일 크기 X 가 기존 데이터와 비슷한 규모(U ≈ 2X)인 최악의 경우 피크 ≈ **4X** 이므로 `X ≤ LIMIT/4` 로 두면 그 경우가 상한 안에 들어옵니다.
- 실측 #6 에서 상한이 2.5M 보다 낮게 나오면 `LIMIT_CHARS` 만 낮추면 됩니다 — **파생식이라 `MAX_IMPORT_CHARS` 는 자동으로 따라 내려갑니다.** 이것이 독립 상수를 없앤 두 번째 이유입니다.

**2) 확인 대화상자보다 앞에서 용량을 사전 검사합니다 — 검증 순서에 `V-3-1` 신설** (기존 V 번호는 바꾸지 않습니다):

| # | 검사 | 실패 코드 |
|---|---|---|
| V-3 | 파일 문자 수 > `MAX_IMPORT_CHARS` | `E-408` |
| **V-3-1 (신설)** | `JR.store.mode() === 'memory'` 가 **아니고** `usage().usedChars + 2 * text.length > JR.store.LIMIT_CHARS` | **`E-413`** |

- 메모리 모드에서는 저장소 상한이 의미가 없으므로 **건너뜁니다.**
- `2 * text.length` 인 이유: 새 데이터는 본체 + `.bak` 2벌로 들어갑니다. `usedChars` 에는 트랜잭션 직전 사용량(= 곧 만들어질 롤백 사본과 같은 크기)이 이미 반영돼 있습니다.
- **파괴적 확인 대화상자를 띄우기 전에 막습니다.** "모두 사라집니다"에 동의시킨 뒤 용량 부족으로 실패하는 순서를 허용하지 않습니다.

| 항목 | 값 | 근거 |

#### INT-28 · INT-12 4항을 **"채우지 않되 지우지도 않는다"로 축소** (Q-023 · ④ 권고안 1번 채택)

**INT-12 4항을 아래로 교체합니다.** (1·2·3·5·6항은 그대로입니다.)

> **4항 (개정)**: 3항의 조건을 만족하지 않으면 **초안을 그대로 남겨 둔 채** 기본값으로 폼을 엽니다. **`clearDraft()` 를 부르지 않습니다.** 그 초안은 원래 대상(모드·`targetId`)의 화면에 들어갈 때 복원되고, 아무도 열지 않으면 §6-6 의 24시간 만료가 정리합니다.
> 예외 1건 — `loadDraft()` 가 `data.code === 'E-603'`(24시간 만료)로 반환한 경우에는 **기존대로 폐기하고 T 슬롯 `E-603`** 을 띄웁니다. 이것은 §6-6 이 정한 만료이지 "다른 화면의 것"이 아닙니다.

- **사유**: 기존 4항은 §6-6 의 원칙 "명시적으로 나가면 버리고, **사고로 사라지면 되살린다**"를 정면으로 위반했습니다. 「기록 X 수정 중 → 백그라운드 정리 → 재진입 시 S-01(INT-12 1항) → `+ 지출 추가` 누름 → X 의 초안 소멸」 경로에서 사용자는 **되살릴 기회를 한 번도 받지 못하고, 알림조차 받지 못합니다.** "지금 화면의 것이 아니다"는 **채우지 않을 근거로는 타당하지만 지울 근거로는 성립하지 않습니다.**
- 비용: 없음. 초안 키는 단수(`jr.v1.draft`) 1개뿐이라 용량 부담이 없고, 만료 규칙이 이미 있어 새 정책이 필요 없습니다.

**부수 확인에 대한 답 — 단수 초안 키는 v1 의도입니다.** `jr.v1.draft` 는 단수 키이므로 add 초안과 edit 초안이 **동시에 존재할 수 없고, 새 초안이 실제로 저장되는 순간(사용자가 다른 화면에서 입력을 시작한 순간) 앞의 초안이 덮어써집니다.** 이것은 의도된 v1 제약입니다. 위 개정으로 「화면에 들어가기만 해도 지워지는」 경로는 사라지지만, 「실제로 다른 내용을 입력하면 덮어써지는」 경로는 남습니다.

- 이 덮어쓰기는 **알리지 않습니다.** 구조설계 §7-9 「알리지 않고 처리하는 것」 표에 다음 행을 추가한 것으로 취급합니다 — 「다른 대상의 초안을 새로 작성해 앞 초안이 덮어써짐 / 덮어씀 / **사용자가 지금 쓰고 있는 내용이 최신이며, 초안은 저장이 아니라 임시 보관입니다. v1 은 초안 1건만 보관합니다**」. **⑤ QA 는 이것을 결함으로 올리지 마십시오.**
- 다중 초안은 **v2 항목**입니다(§2-3 에 추가).

### 7-10. `design-lead` 2차 제기분 판정 (INT-32 · INT-33) — 2026-08-18

**1) 먼저 실측 — ③ 의 전제 1건이 틀렸습니다**

③ 은 「종전 최장은 `E-121` 74자」라고 적었습니다. ② 가 구조설계 §7-1~§7-6 표의 **T 슬롯 코드 34개 전부를 세어** 확인한 결과, **`E-403` 이 77자로 `E-121`(74자)보다 깁니다.** `E-413` 신설 이전에도 최장은 `E-121` 이 아니었습니다. (이 사실은 ③ 소유 문서에 있으므로 ② 가 고치지 않고 `handoff/02-기획.md` **§12-2** 로 정정 요청했습니다.)

**T 슬롯 34개 길이 분포 (INT-32 이전 기준 · ② 전수 계수 · 치환 변수 `{over}`·`{count}`·`{percent}` 는 대표값으로 계산)**

| 구간 | 개수 | 코드 |
|---|---|---|
| 21~55자 | 31 | 나머지 전부(최단 `E-602` 21자) |
| 66~80자 | 2 | `E-121` 74 · `E-403` 77 |
| 81자 이상 | 1 | `E-413` 87 (→ INT-32 로 B 이동) |

**2) T 슬롯 적격 기준 (② 확정) — 아래 2조건을 **모두** 충족해야 T 입니다**

> **(가) 재현 비용**: 문구를 놓쳐도 **같은 화면에서 조작 1회**로 같은 문구가 다시 나와야 합니다.
> **(나) 복구 절차의 범위**: **실패한 조작을 성공시키기 위해 필요한 복구 절차**가 **2개 이상의 화면을 거쳐야 하면 T 에 담지 않습니다.** 화면을 옮기는 순간 문구가 사라지기 때문입니다.

- **(나) 는 "조작이 이미 성공한 뒤의 권고"에는 적용하지 않습니다.** 예: `E-204`(저장은 됐지만 백업본 실패 → "설정에서 내보내기 권합니다")는 지시가 다른 화면을 가리키지만 **그 조작은 이미 성공**했으므로 놓쳐도 사용자가 손해를 보지 않습니다. **T 유지.**
- **전수 적용 결과**: T 슬롯 34개에 위 두 조건을 전부 대입한 결과 **위반은 `E-413` 1건뿐**입니다. 기준을 결론에 맞춰 만든 것이 아니라, 독립적으로 세운 기준이 ③ 이 지목한 그 코드 하나를 정확히 집어냈습니다. 나머지 33개는 조건을 만족합니다(`E-113`·`E-117`·`E-118`·`E-401` = 같은 화면 · `E-119`·`E-122`·`E-124`·`E-306`·`E-308`·`E-309`·`E-409`·`E-605` = 조작 완료 통지 · `E-5xx`·`E-402`·`E-502`·`E-507`·`E-599` = 새로고침(화면 이동 아님)).

**3) T 슬롯 문구 길이 상한 (② 확정)**

| 상한 | 값 | 근거 |
|---|---|---|
| **전체 길이** | **65자 이하** | ③ 실측: 360px 뷰포트에서 87자 = **5줄** → **17.4자/줄**. 4줄 = 69.6자이므로 **65자면 4줄 안에 확실히 들어갑니다.** 토스트가 5줄 이상이 되면 탭바(56px) + 간격 + 토스트가 640px 화면 하단의 30% 이상을 덮어 사용자가 조작 중인 요소를 가립니다 |
| **첫 문장 길이** | **32자 이하** | 같은 실측으로 **2줄(34.8자) 이내**. 3초 · 한국어 통상 6자/초 = **18자**가 실제로 읽히는 양이므로, 첫 문장이 2줄을 넘으면 **첫 문장조차 끝까지 읽히지 않습니다** |

**왜 18자를 상한으로 삼지 않는가**: 18자는 **완독** 기준입니다. 위 (가)(나)를 통과한 T 코드는 **완독을 요구하지 않는 것만 남으므로**(놓쳐도 조작 1회로 다시 나오거나, 이미 끝난 일의 통지) 완독 기준을 상한으로 쓰면 어떤 실용적 문구도 통과하지 못합니다. 대신 **구조설계 §7-0 문구 원칙 1(「무엇이 어떻게 됐는지 먼저」)** 이 이미 첫 문장에 결과를 놓도록 정하고 있으므로, 3초에 읽히는 앞부분만으로 사실이 전달됩니다. **길이 상한은 독해 속도가 아니라 레이아웃에서 나옵니다.**

**4) 상한 위반 3건의 처리 — 문구는 ② 소관이므로 ② 가 새 문구를 확정합니다**

**`E-403`** — 구조설계 §7-4 표의 문구를 아래로 교체합니다. **77자 → 64자**

> `파일을 읽지 못했습니다. 파일이 열려 있거나 접근이 막혀 있을 수 있습니다. 다른 위치에 복사한 뒤 선택해 주세요.`

- 뺀 것: `다른 프로그램에서`(원인 예시 · "열려 있거나"만으로 전달됨) · `다시`(`선택해 주세요` 와 중복).
- 유지한 것: 결과(읽기 실패) · 원인 2가지(열림 / 접근 차단) · 행동(다른 위치에 복사 후 선택). **정보 손실 없음.** 첫 문장 13자.

**`E-121`** — 구조설계 §7-1 표의 문구를 아래로 교체합니다. **74자 → 61자**

> `메모가 100자를 넘어 저장하지 못했습니다. 이모지는 보이는 것보다 글자 수가 많습니다. 메모를 줄여 주세요.`

- **문장 순서를 뒤집었습니다.** 원문은 첫 문장이 이모지 계산 방식 설명(`이모지는 눈에 보이는 개수보다…`)이고 **실제 결과(저장 실패)는 두 번째 문장**이었습니다. 이것은 **구조설계 §7-0 문구 원칙 1(「무엇이 어떻게 됐는지 먼저」) 위반**이며, 이번 검사에서 새로 발견한 것입니다. 3초 안에 읽히는 앞부분에 결과가 오도록 바로잡았습니다.
- 유지한 것: 결과 · 이유(이모지 계산) · 행동(메모 줄이기). 첫 문장 24자.
- **이 코드가 INT-29 T 우선순위 2위입니다.** 서문에서 말한 「Q-024 와 Q-026 이 겹치는 지점」이 이 한 줄로 닫힙니다.

**`E-306`** — 구조설계 §7-3 표의 문구를 아래로 교체합니다. **35자 → 29자 (첫 문장 = 전체 29자)**

> `카테고리 순서가 어긋나 이름순으로 다시 정리했습니다.`

- 뺀 것: `있어` 2자와 조사 조정뿐입니다. 의미는 동일하고 한 문장 구조도 유지됩니다.
