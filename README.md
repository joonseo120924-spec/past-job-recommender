# past-job-recommender

과거 경력(직무·기간·산업·사용 스킬·성과)을 입력하면 다음으로 옮겨갈 만한 직무를 추천하고, 그 직무를 위해 채워야 할 **스킬 갭**을 함께 보여줍니다.

런타임에 외부 API나 LLM을 호출하지 않습니다. 추천은 저장소 안의 직무 데이터와 로컬 벡터 연산만으로 계산되므로, 인터넷 없이 그대로 실행됩니다.

## 실행

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload
# http://127.0.0.1:8000
```

테스트:

```bash
pytest
```

## 동작 방식

### 왜 한국어 텍스트를 그냥 TF-IDF에 넣지 않는가

`TfidfVectorizer`의 기본 토큰 패턴은 한국어의 교착어 특성을 처리하지 못합니다. `데이터를` / `데이터의` / `데이터` 가 서로 무관한 세 개의 토큰이 되어버립니다. 그래서 이 엔진은 **한국어 산문의 어절 분리에 의존하지 않습니다.**

피처 공간은 두 블록으로 나뉩니다.

| 블록 | 내용 | 역할 |
|---|---|---|
| **A** | 통제된 스킬 어휘 + 직무계열/산업/연차 토큰 (직접 토큰화) | 실제 판별 신호 |
| **B** | 자유서술(성과, 직무 요약)의 **문자 n-gram** (2~4) | 보조 신호, 가중치 0.35 |

블록 B를 낮게 누르는 이유는 두 가지입니다. 산문은 노이즈가 많고, 사용자가 쓴 성과 텍스트는 **검증되지 않은 입력**이라 키워드를 채워 넣으면 점수가 움직입니다.

사용자가 입력한 스킬은 별칭 정규화(NFKC, 대소문자, 공백 제거)를 거쳐 어휘에 **정확히 일치할 때만** 인식됩니다. 근사 매칭을 하지 않는 것은 의도적입니다 — 엉뚱한 스킬로 조용히 잘못 매칭되는 것보다, 인식 실패를 UI에 그대로 노출하는 편이 낫습니다. `/api/normalize` 와 자동완성이 그 역할을 합니다.

### 점수 계산

```
최종점수 = 0.55 · 스킬유사도
         + 0.22 · 경력적합도
         + 0.12 · 직무전환 인접성
         + 0.11 · 산업 연관성
```

각 과거 경력에는 가중치가 붙습니다.

- **최근성**: 반감기 5년의 지수 감쇠, 하한 0.15. 5년 전에 끝난 일은 절반, 10년 전은 1/4로 세지만 완전히 사라지지는 않습니다.
- **재직기간**: log 포화, 5년에서 1.0. 같은 일의 2년차는 8년차보다 많이 배웁니다.

**경력적합도**는 환산 경력이 직무의 연차 밴드 안에 있으면 1.0입니다. 미달일 때의 페널티가 초과일 때보다 큽니다 — 1년차에게 시니어 직무를 추천하는 것이 사용자가 가장 황당해하는 실패이기 때문입니다.

**직무전환 인접성**은 데이터셋의 `adjacent_role_ids`(선언된 인접 직무 1.0 / 같은 계열 0.6)를 그대로 씁니다. 데이터가 "이 이동이 자연스럽다"고 직접 말하는 유일한 필드라 텍스트 유사도에 묻지 않고 독립 항으로 뒀습니다.

모든 상수는 `app/engine/constants.py` 한 곳에 있습니다. 테스트는 상수를 **결합하는 연산**을 검증할 뿐 특정 점수값을 고정하지 않으므로, 가중치를 바꿔도 테스트가 무너지지 않습니다.

### 스킬 갭

```
갭 점수 = 중요도 × (1 − 커버리지)
```

커버리지는 스킬을 직접 보유하면 1.0, 아니면 **연관 스킬 1홉**을 통해 부분 인정(최대 0.6배)을 받습니다. 부분 인정은 항상 사용자가 실제로 입력한 스킬을 근거로 제시합니다("보유한 'A/B 테스트 설계' 경험으로 …"). 1홉만 허용하는 이유는 설명 가능성을 유지하기 위해서입니다.

스킬 연관도와 산업 인접성은 **손으로 쓴 표가 아니라 데이터셋 자체의 동시출현(Jaccard)에서 유도**합니다. 관리해야 할 진실의 원천이 하나뿐이도록 하기 위해서입니다. 다만 한 직무에서만 함께 등장한 쌍이 우연히 1.0을 받지 않도록 근거량으로 감쇠시킵니다.

## API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/` | 입력 폼 (단일 HTML, 빌드 단계 없음) |
| POST | `/api/recommend` | 추천 + 스킬 갭 |
| POST | `/api/normalize` | 엔진이 무엇을 인식했는지 미리보기 |
| GET | `/api/roles` · `/api/roles/{id}` | 직무 목록 / 상세 |
| GET | `/api/skills?q=` | 스킬 자동완성 |
| GET | `/api/industries` | 산업 목록 |
| GET | `/api/health` | 로드된 데이터 규모 |

## 데이터

`data/job_roles.json` — 8개 계열 **48개 직무**, 통제된 스킬 어휘 **252개**, 산업 20개.

`tests/test_data_integrity.py`가 실제 데이터에 대해 검증합니다: 인접 직무 참조 무결성, 스킬 표기 일관성(`데이터 시각화` / `데이터시각화` 혼용 금지), 필수/우대 스킬 중복, 고아 직무 등. 데이터가 조용히 품질을 떨어뜨리는 가장 큰 원인이라 별도 스위트를 뒀습니다.

## 알려진 한계

솔직하게 적어둡니다. 이 한계들은 가중치를 조정해서 해결되지 않습니다.

1. **IDF가 노동시장이 아니라 데이터 작성자의 문체를 반영합니다.** IDF는 원래 대규모 코퍼스에서 학습되는 값인데, 여기서는 손으로 쓴 48개 문서에서 나옵니다. `Python`을 40개 직무에 적어 넣으면 Python 경력이 변별력을 잃습니다.

2. **가중치는 학습된 값이 아니라 근거 있는 추정입니다.** 라벨 데이터가 없어 0.55/0.22/0.12/0.11, 반감기 5년, 부분 인정 0.6은 모두 검증되지 않았습니다.

3. **점수는 서열 지표이지 절대 평가가 아닙니다.** 짧은 희소 문서의 코사인 유사도는 좁은 구간에 몰려서, 좋은 매칭이 69점, 그저 그런 매칭이 58점으로 나옵니다. UI가 원점수 대신 **순위와 역량 충족률**을 앞세우는 이유입니다.

4. **성과 텍스트에 쓴 내용은 스킬로 인식되지 않습니다.** "퍼널 분석으로 전환율 개선"이라고 써도 `퍼널 분석`은 갭으로 남습니다. 성과 텍스트는 블록 B(문자 n-gram)에만 들어가고, 스킬 인식은 스킬 입력란의 통제 어휘로만 이뤄집니다. 의도된 동작이지만 사용자에게는 의외로 보일 수 있습니다.

5. **유사 직무가 상위권에 몰릴 수 있습니다.** 데이터 분석가에게 가장 유사한 직무는 BI 분석가, 그로스 분석가입니다. 다양성 보정(MMR 등)은 넣지 않았습니다 — 튜닝할 데이터가 없는 상태에서 조정 손잡이만 늘리기 때문입니다.

6. **직전 직무만 추천에서 제외됩니다.** 과거에 했던 다른 직무는 "돌아갈 수 있는 선택지"로 남아 추천에 다시 등장할 수 있습니다.

7. **별칭 테이블은 수작업 부담입니다.** 사용자가 어휘에 없는 표기로 입력하면 인식되지 않습니다. 근본 해결책은 `kiwipiepy` 같은 형태소 분석기 도입이며, 현재 범위 밖입니다.
